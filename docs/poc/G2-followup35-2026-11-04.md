### Echoes, UDP and alternative explanations

F22's reads 102/103 take 57.183/80.012 µs (monotonic), versus approximately 1 ms before the timeout. Both return five bytes; B1's next two reads similarly return four bytes in 85.276/73.927 µs. The source [stream](../../tests/netlab/scripts/stream.py) used a single `recv(128)` and only tested for EOF. No response content or comparison was retained. The likely queued-token interpretation (101 then 102, or B1's 43 then 44) is **unverified**; TCP is a byte stream and a recv is not a token boundary. Those exact identities cannot be recovered from lengths or the UDP-only captures.

The timeout path skips UDP entirely. “Zero UDP loss” describes the 103 sent datagrams, and supplies no probe during sequence 101's TCP wait. All three historical captures contain zero TCP header records. Host scheduling delay, responder delay, request loss and reply loss cannot be distinguished for these specific reads. The retained Apply timing shows no install over 100 ms; no sampled suite overlap was reported for isolation 22. B1's [quartet summary](G2-followup27-evidence/comparison-summary.json) records quiet entry/exit (entry idle 97–100%, exit 95–100%) and empty suite/timing-process checks. That strengthens the absence of a documented host explanation, without excluding an unsampled delay. There is no affirmative evidence assigning the 1.5-second delay to the host or responder. Production's dropping guard is independently proven by f30, but the exact attribution of F22-01 and F27-01 remains open.

## Agent Apply cadence (read-only inspection)

All citations below refer to the source tree above. **There is no positive enforced minimum Apply spacing**: serialization prevents concurrent Applies, but there is no cooldown. “At least one second” describes the configured ordinary Step period, not Apply-to-Apply spacing.

| Path | Code and minimum spacing |
|---|---|
| Ordinary new generation | [serving.go:12](../../node/agent/serving.go#L12) takes the smaller positive integer-second heartbeat/poll interval; [sync.go:185](../../node/agent/sync.go#L185) defaults heartbeat to 10 s. But [serving.go:20](../../node/agent/serving.go#L20) subtracts the elapsed Step duration and clamps the wait to **zero**. Applies occur later within each Step at [engine.go:780](../../node/agent/engine.go#L780), not at Step entry. Example: Step starts at 0, first Apply starts at 0.85 s, Step finishes at 0.95 s, next Step starts at 1 s and applies at 1.05 s: **200 ms between Apply starts**. This is code-path arithmetic, not a live timing claim. |
| Binding deadline / survivors | [engine.go:647](../../node/agent/engine.go#L647) shortens the next delay to `max(0, policyExpires-now)`. [serving.go:129](../../node/agent/serving.go#L129) retains serving siblings; [engine.go:1180](../../node/agent/engine.go#L1180) rebuilds a model after a deadline crossing. [retain.go:33](../../node/agent/retain.go#L33) rejects retention when the deadline/model changes. An Apply starting at 0 and finishing at 80 ms, a binding deadline at 200 ms, and 40 ms of next-Step work permits another Apply at **240 ms**. No one-second floor. Deadlines protect isolation and must not simply be delayed. |
| Grant-less renewal slot | [sync.go:214](../../node/agent/sync.go#L214) anchors the slot to the request time and caps it by the lease renewal lead; [engine.go:653](../../node/agent/engine.go#L653) returns a possibly zero delay to it. [serving.go:27](../../node/agent/serving.go#L27) uses that slot directly when closed. Waiting grant-less state may retain a closed model ([recovery.go:30](../../node/agent/recovery.go#L30)); a changed generation or granted lease defeats that retention. No positive Apply-spacing guarantee follows from this renewal backoff. |
| Recovery | A prior Apply error plus stale-generation lease can install a closed candidate at [engine.go:1118](../../node/agent/engine.go#L1118), acknowledged at [engine.go:1379](../../node/agent/engine.go#L1379). The same Step then calls `renewAppliedLease` at [engine.go:785](../../node/agent/engine.go#L785), which syncs the matching lease and calls `enforce` again at [sync.go:256](../../node/agent/sync.go#L256). `serving=false` defeats the skip ([retain.go:31](../../node/agent/retain.go#L31)). Both reach [engine.go:1303](../../node/agent/engine.go#L1303) without a timer: 80 ms Apply + 20 ms ACK/lease/local work permits a **100 ms** start-to-start gap. Generation-mismatch repair also calls enforce immediately ([serving.go:65](../../node/agent/serving.go#L65)), including from the deferred end-of-Step verification. The updater recovery child has a one-second **child-start** retry floor ([updaterecover.go:14](../../node/agent/updaterecover.go#L14)); it is not an Apply floor. |
| Restart | [engine.go:604](../../node/agent/engine.go#L604) boots then immediately enters the first Step at line 620. Same-boot adoption verifies retained state and installs no candidate ([restart.go:60](../../node/agent/restart.go#L60)); rejection installs a baseline ([engine.go:561](../../node/agent/engine.go#L561)). There is no persisted last-Apply cooldown across processes. Startup/local/control work determines the gap; no code lower bound of 400 ms or one second is enforced. Baseline is distinct from `Plane.Apply`. |

Additionally, SIGHUP stops the timer and starts the next Step immediately ([engine.go:631](../../node/agent/engine.go#L631)). The advisory “one Apply per Step” is false for recovery. Even restricting attention to ordinary single-Apply serving Steps would not establish a one-second Apply floor.
