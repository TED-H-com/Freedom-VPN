Product diagnosis at baseline `04d31ea5` (includes agent-core 49, #454):

- `node/agent/sync.go:85–166` attempts at most one renewal per Step and honors
  Retry-After. Missing/unfresh lease, invalid anchor, pending refresh, retry,
  and lease/applied (or failed-apply desired) generation mismatch request one.
  Grant-less leases use heartbeat-based exponential waits capped at 60 seconds
  (`sync.go:177–226`). An ordinary granted lease renews only when its **own**
  monotonic remaining lifetime reaches `renewLead(window)+jitter`.
- `node/agent/engine.go:1547–1555`, `sync.go:262–294` and `config.go:133–134`
  define lead as max(1s,min(configured lead,window/2)), default 120s, with a
  saved uniform ±10% jitter. `sync.go:25–36` makes desired-state 304 a no-op for
  lease time. `engine.go:783–785` and `sync.go:233–259` request a matching lease
  in the Step that applies a new generation (or the next eligible Step if a
  renewal already ran). Restart is a separate refresh path
  (`node/agent/restart.go:132`); this setup does not require it.
- `internal/nodes/httpwire/fleet_config.go:54–67` updates only cap, resource
  version and updated_at. It does not bump desired generation or enqueue
  renewal. `internal/leases/leases.go:315–325` reads the cap at issuance.
  `contracts/openapi.yaml:2487–2491,2529–2540` explicitly makes this nonretroactive.
- Run `1bfd5cff` set the cap at `2026-11-04T04:35:23.829257Z`, but the accepted
  lease `f6b7e639-c508-44f6-af68-b25ac251a9d3` had generation 17, issue time
  `2026-11-04T04:33:00.436641756Z`, and a full 86,400s duration. Under the
  default lead its scheduled renewal is roughly the next day at 04:30:48 to
  04:31:12Z, not within that setup's 90 seconds (the fixture generator at `tests/e2e/cmd/fvpn-e2e-prepare/main.go:387–410` does not override the 120s default). Earlier member deadlines can
  remove individual forwarding but do not change this ordinary node-lease
  renewal calculation. No new desired generation was triggered after its cap
  PUT. A cap-only wait has no prompt-refresh mechanism and did not produce the prerequisite in this run.

In addition to worker event processing, each node GET of desired state calls
`CompileControlState` (`internal/nodes/httpwire/state.go:62–149,152–166`). It
reads current update, policy, entitlement and binding inputs. Its signer reuses
the cached generation only when the complete document is unchanged after
normalizing generation/timestamps (`state_cache.go:21–47`). This is also the
concrete path for node capacity/group and fleet update/support changes; it does
not rely on an undocumented push notification. A freshness refresh may also
create a generation once the desired envelope's remaining lifetime is below
half its configured TTL (`state.go:127`), independently of the fleet lease cap.
The previous 90s wait observed no such refresh; the cap write cannot schedule it.

The compiler's exhaustive event dispatch is
`internal/desiredstate/compiler.go:30–42,959–1094`, and it persists the new
node generation at `compiler.go:648–654`. The agent's generation-mismatch
renewal path above is common to those actual changes. No-op/idempotent replays
are not a guarantee of fresh generation; neither are GETs or a bare cap PUT.
Node revoke/retire removes serviceability (`internal/leases/leases.go:345–349`),
so it cannot obtain a usable short lease. There **are** public generation-change
routes for a running node; no missing-public-route product finding is warranted.

The setup wait reads only the accepted local SQLite lease through the existing
read-only helper. It requires issue time strictly after the confirmed cap's
updated_at, signed cap 60, lifetime in (0,60s], correct positive monotonic anchor,
member coverage, the existing remaining-window margin and serving heartbeat
whose policy deadline equals D. Timeout retains the exact observed ID, issue
time, cap and duration. The post-disconnection read checks issuance/cap again
in case a final in-flight renewal completed. Restoration remains registered
before mutation and uses public APIs for fleet cap and finite member standing.
Control/worker process faults are reversed through their existing harness calls.
