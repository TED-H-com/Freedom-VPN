### H-1: confirmed engine API defect; neither CLI mode reaches the reported path

`bootWithBudget` stores the caller in `runCtx` (`node/agent/engine.go:471`).
`recoverOnce` returns on its cancellation before setting `recoverBlocked`
(`node/agent/updaterecover.go:37–40`); `Step` never replaces it
(`engine.go:676–695`). A canceled Boot followed by a live Step can therefore
admit forwarding without recovery (`input`, `engine.go:940`; recovery gate,
`node/agent/decide.go:146–147`). A canceled per-call Boot after busy recovery
instead keeps `recovery_required` forever, even after lock release. An in-flight
child also inherits that Boot context (`updaterecover.go:62–86`) and is killed
when the call's context ends. Both effects last for that engine's lifetime.

The first r30 proof restarts a served rig with `/bin/true` but missing updater
configuration, cancels Boot before entry, then calls Step with a live context.
The second uses exit 3 followed by exit 0 and cancels Boot between calls. Those
are real public Engine API sequences. Its manual clock does not advance between
child attempts: the second proof must also respect the one-second retry floor
(`updaterecover.go:16,59,69`); real elapsed time advances, this rig's clock does
not. Assertions will be preserved with a minimal explicit clock advance if
needed. Neither proof tests an actual running child surviving per-call cancel.

CLI run calls `Run(ctx)`, which uses the same process context for Boot and every
Step (`engine.go:603–631`). CLI once uses the same signal context for Boot and
Step, then defers Close (`node/agent/cmd/fvpn-agent/main.go:96–100,120–135`).
There is no later live Step after cancellation in either CLI mode. Run exits;
a canceled once Step returns at `engine.go:692–693` and Close joins children.

Every production `runCtx` read and its actual need:

| Base location | Need |
|---|---|
| `updaterecover.go:37` | Process stopping: only Run's context has this meaning for the engine API. |
| `updaterecover.go:62–66` | Parent of a long-lived recover child; per-call Boot/Step cancellation must not own it. Run cancellation or explicit stop/Close may end it. |
| `usage.go:232` | Suppress upload startup if its existing caller parent is canceled. |
| `usage.go:236–237` | Parent of the upload loop; currently Boot's caller (the signal context in both CLI modes). |
| `usage.go:243` | Attach Close's loop cancellation when the upload parent is that caller. |

`usage.go:240` is a comment, not another read; `engine.go:98` declares the field
and `engine.go:471` is its only production assignment. Preserve upload parenting
separately: run and once must still cancel request contexts synchronously with
the same signal context, and Close must still cancel/join via `loopCtx`.

### M-2: confirmed, reachable in a real run Step

A grant-less request is sent before desired sync (`engine.go:742–752`) and sets
`leaseAttempted` (`node/agent/sync.go:86,112–124`). Failure or an old-generation
answer can leave the lease behind the new desired document. The same Step can
complete closed recovery and ACK the new generation (`engine.go:1128–1138,
1381–1394`), but `renewAppliedLease` calls the already-consumed per-Step guard
(`sync.go:252–267`). The lease-generation gate stays closed (`policy_missing`),
and `recoveryRenewalEligible` cannot bind a report (`recovery_renewal.go:16–22`).
The r30 proof constructs this using only normal Steps and external fixtures:
generation 14 grant-less lease, foreign tc, repair, a due slot, generation 15,
and one failed lease call. This can occur during run; once can execute such a
Step given equivalent previously established engine state, but a fresh CLI
once Boot has no retained in-memory Apply failure and does not itself produce
that multi-Step history.

This is delay, not unauthorized forwarding or a permanent wedge. On the next
Step the guard resets (`engine.go:691`); the generation mismatch makes renewal
due before the ordinary D-067 slot (`sync.go:159`). After a failed pre-request,
`nextStepDelay` uses the attempt plus the control interval if the old slot has
already elapsed (`engine.go:657–662`); after an old-generation empty answer it
uses that answer's next exponential slot. Retry-After still wins. On the next
successful matching lease, a clean report can bind/arm D-157 and Run wakes
immediately (`engine.go:645–647`). An empty answer advances D-067 as usual
(`sync.go:221–233`). Thus the added delay can be the next poll/slot (capped by
D-067's 60 seconds) plus control failures, not an indefinite recovery latch.

The required same-Step dispatch is the **generation catch-up request** before
the report. The D-157 one-shot follows acceptance of the bound clean report;
r30 explicitly asserts it is armed at recovery-Step return. Preserve that
existing immediate-next-wake behavior and every assertion rather than consume
that opportunity before the report or weaken its receipt gate.

### M-3: reachable with a full outbox and partial drain; direct proof skips that history

`observe` returns before updating `lastObservationState` while `outboxFull`
(`node/agent/observe.go:33,62`). Once space returns, identical state plus any
pending item is deduplicated (`:38–45`), even though a new closed Apply reset
its opportunity and `lastObs` (`engine.go:1381–1384`). The r30 proof directly
calls baseline and `noteApply`, then enforce and observe. It proves the local
dedup defect but does not itself prove a production Step sequence.

A real sequence can fill 32 entries with semantic transitions during observation
backoff, ending with a clean closed-recovery report as entry 32. The next Step
sets `outboxFull` (`engine.go:780–781`); that gate withdraws (`decide.go:140–141`,
`engine.go:1140–1148`). The final blocked audit can detect foreign tc on the
retained model and record an Apply error (`node/agent/serving.go:208–238`), while
observe skips the failure because the outbox is full. Later the first flush can
accept some old entries and fail on another (`observe.go:286–350`). The Step
recounts pending items, now below 32, and a clean same-generation closed Apply
can restore the same semantic observation state. Old pending items remain, so
the new recovery's report is skipped. Full drain would avoid the bug; an
intermediate recorded failure would also change the comparison state.

The cost is prior observation outage/backoff, enough transitions to reach the
32-entry cap (which itself closes forwarding), then partial rather than complete
drain. This can occur in run's repeated Steps; one fresh CLI once pass cannot
create two in-memory closed recoveries. It holds the early-renewal opportunity,
not a forwarding permission. Ordinary D-067 renewals continue. A later full
drain or semantic transition lets the still-due report queue, or a populated
ordinary lease plus verified Apply restores forwarding. There is no finite
bound if observations continue failing; ordinary grant acquisition can recover
without that optimization. A narrow exception for a recovery waiting to bind
its own report preserves dedup in every other case and the 32-entry safety cap.

## Changes and proof design

Recovery closes its gate before checking process cancellation, and `input`
also refuses an unfinished configured recovery. Only `Run` sets `runCtx`.
Its context remains immutable after Run returns because a bounded Boot worker
may still be finishing; clearing it then could race that worker. Run's deferred
`stopRecovery` and Close retain their join behavior. Standalone Boot/Step use
the existing explicitly canceled background child. A canceled per-call Boot
can still run recovery within its independent local budget; it cannot poison
later Steps. A canceled Run spawns nothing and supplies no failure evidence.

Uploads retain exactly their prior parent in `uploadParent`, assigned by Boot.
Both CLI modes still use their signal context; cancellation reaches the HTTP
request synchronously, and loop cancellation on Close still ends uploads. This
also preserves standalone Boot's existing upload behavior; this change only
removes that caller's ownership of the recovery child. The real request-context
proof holds a usage response and checks cancellation before Close in both modes.

Lease requests remember the ACK actually sent (zero for null). A closed Apply
with a newly available ACK can make one generation catch-up request despite an
earlier attempt in the same Step. The retry bound is still checked by syncLease;
recording the new ACK prevents another bypass for that ACK. The accepted clean
report then arms the existing one-shot, which is consumed only by its dispatch.
The proof repeats recovery, tests both a transient pre-request failure and an
old-generation answer, inspects ACKs/IDs, and checks the next D-067 slot after
an empty early answer.

Pending-state dedup now has one exception: an armed closed recovery with no
bound report ID. The capacity guard remains first. The added Step-only proof
uses real queued reports, 32 transitions, an unreported failure while full,
and one accepted old report followed by Retry-After. A second proof checks
coalescing after a report has bound and after the opportunity is gone. Fake
control additions only expose a held upload's request context and permit a
specified number of observation posts before the existing injected failure.

r30 files were imported byte-for-byte in `45cfee9a`. All assertions are kept.
Only its H-1 manual-clock proof adds `Advance(recoverRetryInterval)` before the
second child attempt; the existing one-second retry floor must not be removed
to accommodate a clock that never advances. All four addressed TODO markers
are removed. The watchdog proof remains byte-for-byte unchanged.

Validation is pending host admission. The first bounded admission attempt
returned 125 after 20 held checks (19 thirty-second waits); no test ran. The

Retry-After/ordinary scheduling wake; same-Step catch-up is possible only when

only the new proof, not fake-control failure behavior or any prior proof.

M-2 recovery proof now passes for both failed and old-generation pre-attempts.
