## Recovery contract

`node/agent/updaterecover.go` owns the child and outcome state. Boot and Step can
wait at most 250 ms for a newly started recover command. Later Steps poll its
completion without waiting. A local pass deadline does not kill an open
transaction. The child receives the engine's run context; Run termination and
Close cancel and join it. The child goroutine only publishes a result; Boot/Step
alone change decision fields. A stop/interruption supplies no terminal failure
evidence. At most one child exists, and recovery attempt dispatches are at least one
monotonic second apart, including busy exits. A held-lock precheck spawns none.

The optional empty `updater_recover` setting keeps its prior disabled behavior.
With recovery configured, an empty updater config or exits 1/2 are terminal
blocked; a missing config file reaches the updater and likewise fails terminally.
Exit 3 is unfinished recovery. Success only clears the recovery gate; `Decide`
still requires every other serving condition. No updater journal/stage, lock
scope, completion marker or post-seal restart was changed.

`node/agent/probeexc.go:66–78` (`updateLockHeld`) now uses the same kernel boot ID with the
same configured fallback as `node/updater/engine.go:149–152` (`withLock`). Both use
`node/nodelock/lock.go:AcquireWithBootID`. Only the **bare** `ErrBusy` is live
contention. Stale holder errors wrap it with `boot id`, `pid`, `process` or
`start time`: the agent does not defer for those, and updater
`node/updater/host.go:243–258` (`ExitCode`) keeps them at exit 1. This matches the
[updater 24 hand-off](../updates/node-followup24-2026-11-03.md#agent-core-hand-off-lock-predicates).
Unreadable/malformed metadata keeps the shared library's conservative bare-busy
classification; neither side claims that proves valid holder metadata. Free
flock with an old record is reclaimed normally. No stale lock file is unlinked.

The probe has one nonblocking acquisition attempt. When free it holds the lock
only through the shared helper's holder-metadata write/fsync and immediate
Release; no recovery process, polling, network operation or retry sleep runs
under that descriptor. The recovery child starts **after Release**, so its own
acquisition cannot collide with this probe. Recovery probes once per eligible
Boot/Step while unfinished, never while its child is in flight or after a
terminal result; D-064 retains its challenge checks. The updater's five attempts
at 20 ms tolerate ordinary brief overlap with an independent agent probe; this
is not a measured filesystem/scheduler upper bound. A stalled fsync cannot be
promised to finish in 80 ms on all hosts.

An older updater whose busy status is 1 is handled by the pre-spawn lock check;
exit 3 additionally handles the modern race between that check and acquisition.
Terminal exit 1 is never guessed from stderr or converted into success.

While deferred, D-053 attestation and D-064's exact probe exception continue,
as do lease renewal and watchdog heartbeats. Central receives
`provisioning_state=applying` and `recovery_required`, with member forwarding off.
A renewal may therefore receive a zero-grant provisional lease. After recovery
and latch clearance, a grantless node reports `ready`/`awaiting_member_grants`;
the unchanged D-067 schedule obtains populated grants before serving. This is
r29 §3 Q5a's interaction, not a new central state.

## Restart window

Follow-up 48's expiry capture confirms the ordering:

- The lab requested a restart three seconds before D with lease requests held.
- Old process: `serving rules retained for restart`, generation 3, at
  `2026-11-04T02:16:21.045Z`, with D = `82026347774970` monotonic ns.
- The successor heartbeat had generation 0, serving false, baseline false and
  mono `82023507010125`. The watchdog read it roughly 8.4 ms later and wrote
  `baseline_unverified` at D − 2,832,299,106 ns.
- Adoption then logged `GENERATION_MISMATCH`, followed by `boot_unverified`.
  Last positive was D − 2,863,679,012 ns; first drop D − 2,800,932,539 ns.
  The earlier failed run remains failed. ISO-F6-03 has the same reported
  signature, but this follow-up does not retrospectively prove its attribution.

Follow-up 48 did not reorder startup publication, recovery and the adoption lock,
or add another stage between them. Its heartbeat change removed a 100 ms child
deadline and allowed publication to use Boot's existing 10 s budget. That can
admit a slow publication which previously failed; it does not eliminate the
race, and it is not evidence that the observed window had a particular length.
M-1's bounded recovery and D-156's receipt must be implemented together because
recovery is in this window.

The pending receipt retains the original `Mono` and `PolicyExpires`; it is not
a new serving attestation. Repeated startup cannot refresh that age. A stall
before adoption is withdrawn at the next unblocked watchdog pass after the old
receipt becomes stale, or at D, whichever stops forwarding first. Defaults are
30 s staleness and 10 s polling; a watchdog pass has a 5 s local operation budget.
The kernel's existing per-binding timeouts remain the hard deadline even if both
processes stall. No restart resets any timeout. Missing, wrong-boot, future,
stale or non-serving predecessor receipts get ordinary startup uncertainty.
Refusal, failed Boot and post-attestation cleanup publish ordinary truthful
baseline/uncertainty state, preserving r22 M-3.
