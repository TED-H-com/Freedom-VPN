# Follow-up 50 — 2026-11-04 — closed-recovery renewal (D-157)

## Diagnosis, before code changes

**Verdict: readiness and the renewal slot are serial prerequisites.** Central
must first accept a clean generation-14 observation. For this already enrolled
agent that update is synchronous, not waiting for a readiness job. The next
request nevertheless waited for D-067's five-second slot. The retained evidence
proves that scheduling alignment, but does not timestamp central's readiness
commit, so it cannot assign all 4.968 seconds to avoidable scheduling delay.
An ACK in a lease request alone does **not** make central ready.

### Central's decision and who changes its inputs

- `internal/leases/leases.go:327–375`: the authenticated node must exist, be
  registered, and use its current, matching, unrevoked incarnation. Otherwise
  renewal fails, rather than issuing members. Enrollment completion sets
  registered/current incarnation synchronously (`internal/enrollment/service.go:573`).
  A local TC quarantine does not revoke or reenroll the identity.
- `internal/leases/leases.go:400–441`: an exit must exist, its publication intent
  must be `published`, it must have at least one exit group, provisioning must be
  `ready`, and no identity endpoint may be mapping-frozen. These are the exact
  `includeMembers` conditions. Publication/group writes are synchronous admin
  command changes (`internal/exits/exits.go:501–535`, `internal/exits/groups.go:16–33`),
  with downstream compile/NetBird work asynchronous. Recovery observations do
  not republish the exit or change groups.
- Mapping freeze is an identity conflict fence, not TC quarantine. Endpoint
  observation runs synchronously on the report and renewal request
  (`internal/nodes/httpwire/handlers.go:310–330`, `state.go:188–200`); a detected
  conflict freezes mapping and marks failed in that same transaction
  (`internal/enrollment/revoke.go:382–408`). Frozen
  observations remain failed (`internal/nodes/observations.go:163–169`), and the
  worker refuses discovery/binding on frozen identities
  (`apps/worker/jobs_nodes.go:192–195,228–236`). Clean Apply does not clear it.
  Such a recovery cannot use an observation to bypass the identity fence.
- Readiness normally changes **within SubmitObservation's transaction**:
  `internal/nodes/observations.go:160–169,245–315,410–423`. The command
  middleware returns the response only after `db.InTx` commits
  (`internal/httpapi/commands.go:151–184`, `internal/db/tx.go:77`), so observing
  acceptance follows the readiness write. A ready report needs
  effective safety passed and a positive applied-generation ACK at least as new
  as desired. The one-report stale-generation grace requires an already-ready
  node and is not the quarantine recovery path. Older observations do not
  replace current state (`:281–286,396–407`). A reported management peer ID
  with no bound peer can defer readiness (`:275–278`). `node.peer.observe` then
  performs external read-back, binds the peer and conditionally marks ready in
  a later worker transaction (`apps/worker/jobs_nodes.go:182–266`). **This agent
  sends a null peer ID** (`node/agent/observe.go:136–138`); a normal closed
  recovery therefore does not depend on that worker. Even a previously unbound
  incarnation's null-ID baseline report is not blocked by that predicate.
- Effective safety requires passed internet-only isolation and meter-path
  evidence; D-067 permits absent/not-run (never failed) meter-path while
  forwarding is false and `awaiting_member_grants` is reported. Userspace
  NetBird, failed safety checks, isolation apply errors or baseline/meter errors
  override a passed claim (`internal/nodes/observations.go:495–565`). A clean
  ready report carrying the generation ACK supplies the recovery inputs in one
  request. The HTTP lease handler calls RenewTx without updating readiness
  from its ACK (`internal/nodes/httpwire/state.go:179–207`);
  `internal/leases/leases.go:463–464` signs central's desired generation.
- Even when `includeMembers` is true, grants require an eligible member:
  active, neither member nor entitlement admin-suspended, entitlement state not
  pending-payment/suspended/expired/closed, currently within its validity
  interval, and intersecting exit groups (`internal/entitlement/serving.go:36–44`).
  Member/entitlement administration and projection own these inputs, not node
  recovery; admin commands recompute synchronously
  (`internal/members/service.go:296,394,476,539`); entitlement projections are persisted by
  `internal/entitlement/store.go:44–164`. Time-driven transitions are handled
  later by `members.reconcile` (`apps/worker/jobs_members.go:152–180`,
  `internal/entitlement/store.go:240–269`); quarantine recovery itself does not
  enqueue or await an entitlement transition. Lease construction also rejects an empty
  effective interval and caps its end by offline/node/service deadlines
  (`internal/leases/leases.go:588–638`). Eligibility is rechecked under row locks
  before commit (`:490–513`). Authorized/unrevoked/unfenced devices are read
  (`:162–187`) but their count is not a condition for a MemberLease entry.
- Replaying a renewal request returns the original signed envelope without
  recomputing grants (`internal/leases/leases.go:378–394`). An early renewal must
  have a new request ID. Registered/published but not-ready or mapping-frozen
  nodes get the D-067 60-second lease cap (`:443–451`). Data health, publication
  observed state and member-forwarding observed are not direct includeMembers
  inputs. Their downstream jobs are not prerequisites for this renewal.

### Agent ordering and schedule before D-157

`node/agent/engine.go:735–790` renews before Apply, then applies, attempts a
post-Apply renewal only for a mismatching generation, and observes/flushes.
`node/agent/sync.go:245–259` therefore does nothing after a closed Apply whose
held empty lease already names the applied generation. Closed recovery clears
applyError and records the generation ACK only after full verification
(`node/agent/engine.go:1340–1379`); it never serves. Its first local heartbeat
can still reflect the pre-Apply failed decision (`:1441`). Local heartbeat files
are for the watchdog; they are not central observation receipts.

The end-of-Step observation can likewise carry that earlier failure. The retained trace then has a clean provisional heartbeat. The intervening
health-answer path can refresh the decision when a matching challenge needs a
probe (`node/agent/attest.go:103–127`, `engine.go:948–950`,
`probeexc.go:241–246`). Deferred `finishServingStep` audits the closed state,
writes its heartbeat and observes/flushes (`serving.go:184–207`); it does not
unconditionally recompute a clean decision. Without that intervening refresh,
the next Step's evaluate supplies it. The excerpt does not retain the challenge
or report bodies to prove which refresh occurred. `observe.go:24–62` queues state
transitions immediately; `:70–78,114–138` includes the ACK and safety/readiness;
`:285–360` sends the durable outbox and handles acceptance/backoff. Consequently
central can receive both the failed and then clean report during this Step.
Only acceptance of the clean report is useful for the early-renewal trigger.

`sync.go:85–148` respects one request per Step and Retry-After, sends a fresh
request ID and includes the applied ACK only with no apply/freeze uncertainty.
`needRenew` (`:151–167`) treats a same-generation empty lease as provisional.
`noteProvisionalSchedule` (`:214–226`) anchors its next attempt at the request
start; `provisionalWait` (`:196–208`) waits one heartbeat, then doubles up to
60 seconds, bounded by the renewal lead. `serving.go:27–31` and
`engine.go:643–658` wake on that deadline. D-135/D-136 and `retainClosedRecovery`
(`recovery.go:30–58`) retain the verified deny-all during the wait.

### Proposed agent scope

Arm one opportunity on a verified closed recovery. Once its current-generation
clean ready observation is accepted, wake the renewal path without waiting for
the provisional slot. Preserve Retry-After and one request per Step; consume the
opportunity on dispatch, including an empty answer or transport failure. Empty
answers continue the existing D-067 streak from that request. A later genuine
closed recovery receives its own opportunity. No central code change is needed.

## D-157 implementation and deterministic evidence

`node/agent/recovery_renewal.go` ties a process-local opportunity to one verified
closed Apply and one newly queued clean report ID. The report must carry the
current ACK, passed safety/internet-only checks, no failed meter path or
central-rejected safety errors, and null management peer ID. Acceptance must
match its ID and not freeze the identity. Older queued reports cannot arm a
new recovery. A baseline or replacement Apply discards the opportunity.

`engine.go` forces a fresh observation for each closed Apply and refreshes the
post-recovery decision before reporting, rather than
relying on a health challenge to refresh it. `observe.go` records the accepted
receipt. `needRenew` and `nextStepDelay` then permit one immediate control pass;
the early request follows the accepted report and includes the applied ACK.
The existing one-request-per-Step and Retry-After limits remain. Dispatch
consumes the opportunity even on a transport failure or empty reply. The latter
continues `noteProvisionalSchedule`'s existing streak (5 seconds then 10 seconds
with this fixture); it neither resets the streak nor grants another early try.
`retainClosedRecovery`, D-135/D-136 baseline logic, D-155 deferred recovery and
D-156 restart receipts are untouched. Only a populated matching lease followed
by verified Apply can restore forwarding.

Receipt acceptance is not a new central authorization: concurrent publication,
entitlement, generation or identity changes can still produce an empty lease.
The agent supplies the recovery inputs central reads, then accepts central's
signed decision. There is no readiness polling loop or new production interval.

The manual-clock engine proof starts serving generation 13, injects foreign TC,
receives generation 14 with zero grants, performs closed Apply, and inspects the
accepted report before allowing the fake issuer to provide grants. It checks
that the pre-Apply request omits the ACK, the early request has a new request ID
and ACK 14, forwarding opens only after the populated Apply, and no extra
baseline occurs. It calls Run's actual delay calculation without a wall sleep.
