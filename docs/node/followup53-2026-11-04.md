## 4. F31-01: structural source-binding verification proposal

**Design only.** Current-code citations refer to `466f1510`. The primary records are `docs/e2e/runs/2026-11-03/followup31/source-binding.md` and the F31-01 row in `docs/handover/README.md:357`. They record no hook and zero stack attempts. This round implements no source-binding product behavior or devstack hook.

### What is present, and what a new check could prove

Current `bindingOK` comes from signed model construction (`node/agent/decide.go:208–245`); its failure paths also affect QoS, and retained Apply errors override lease/qos/source_binding together (`node/agent/decide.go:360–371`). It is not an independent live member-source verifier. Current kernel reads do provide structural evidence:

- `node/enforce/verify_tc.go:130–155` reads the whole nft ruleset and checks it against the model; later TC reads reject foreign filters/redirects and verify shaping. `node/enforce/verify.go:822–858` checks each device accept's host-side address and assigned class. `node/agent/allowed_presence.go:43–94` checks live allowed_v4 presence with the existing deadline reserve; `node/enforce/deadline_read.go` verifies bounded lifetimes. Shared errors do not yet identify an independent source-binding cause.
- `node/agent/memberpath.go:37–118` reads interface/address state, IPv4 and IPv6 routes and the kernel's route-get decision for each allowed prefix. `readMemberPath` at `node/agent/memberpath.go:121–132` compares retained address/route hashes through MemberPath. Its rejection currently becomes a shared Apply error (`node/agent/memberpath.go:135–143`).
- `auditBlocked` (`node/agent/serving.go:208–236`) reads VerifyServing, handles foreign TC/quarantine evidence, and retains TC readback. It does **not** perform the proposed source-binding route comparison during holds. Adding that comparison is new behavior.

Recommended proposed scope: distinguish **structural source-address admission and return-path validity** from QoS and lease eligibility. A coherent read must show that every authorized pre-SNAT source has the exact expected nft accept/class and allowed-set membership/lifetime, that no extra source accepts or bypass paths exist under the supported verifier model, and that the kernel resolves each expected return destination to the retained member interface. TC evidence excludes the inspected redirect/filter bypasses. Node SNAT is a node egress address, not the member's original bound source.

These structures do **not** prove which device originated a packet using an admitted address. A return route or nft source match cannot authenticate a peer or rule out sibling address spoofing. Full per-device origin proof would additionally require an authenticated live peer-to-AllowedIPs association for the pinned tunnel implementation, comparison with signed bindings, and adversarial packet tests. That reader/capability is not established here. Do not label the structural proposal as proof that each device can originate only its own address, or close the broader acceptance gap on this design alone.

During a populated hold, the proposed verifier uses the retained acknowledged model/binding identity and retained topology hashes as its expectation. Empty authorization sets and deny-all forwarding are expected hold behavior, not a missing-admission fault. It checks retained topology/route resolution and baseline safety separately. It must not union an unacknowledged candidate into the retained expectation. A missing or unreadable retained expectation is unknown/failed evidence, never a clean source-only restoration. The scope and snapshot generation must be carried in the new result.

### Proposed independent reporting and forwarding behavior

All identifiers in this paragraph are **proposed additions**, not current fields/codes: an enforce reason `ReasonSourceBinding`; API code `SOURCE_BINDING_INVALID`; `SourceBindingError` on agent Input and corresponding engine state; and an optional `ObservationReport.source_binding_evidence` with mode (serving or retained hold), expected generation, read time, independent status and bounded diagnostic. Exact schema names need contracts-owner approval. The diagnostic should identify the cause and bounded device identity/model digest without dumping addresses, destinations, packet data or raw kernel stderr (SEC02).

Proposed failure details distinguish an absent/mismatched allowed source, a device accept's wrong host-side address, and a kernel-selected return path outside the retained member interface. A read failure/timeout is not a verified healthy result. A source-only failure sets source_binding to the cause-specific code/detail and adds a source_binding-stage error; it blocks forwarding and makes safety failed. It does not overwrite an otherwise sound lease or QoS result. Other independent errors remain present. D-126 precedence for independent Apply/dependency failures remains: no source result can turn such a report into a pure lease hold.

During a continuing stale lease, removal of the source fault would restore the **independent evidence** to passed while the dependent source_binding check returns to its existing lease-dependent sentence. The lease gate still prevents serving. This separate evidence is necessary to distinguish restoration from a forced check-field change. It composes with F17 option (i): the dependent QoS sentence stays intact, and its retained serving read remains available separately. Central must continue classifying an actual source error as check_failed; absence of that error alone is insufficient for stale_generation classification or serving.

### Cost, cadence and kernel route selection

Current `stepInterval()` is the minimum of the configured heartbeat interval and a positive configured poll interval (`node/agent/serving.go:12–17`). `servingReadTimeout()` is **min(1 second, stepInterval()/2)** (`node/agent/serving.go:36–38`). There is no universal 1–10 s cadence or fixed 500 ms timeout. The context bounds executor work; scheduling and subsequent processing still need measurement.

A successful complete MemberPath pass performs **3 + A** subprocess reads: address state, IPv4 route list, IPv6 route list, then one kernel route-get for each AllowedV4/AllowedV6 prefix (`node/agent/memberpath.go:55,81,95–101`). A is total prefixes, not number of devices; 2N+3 applies only to exactly two prefixes per binding.

Keep kernel route resolution. Longest-prefix matching over route-show tables alone is not equivalent: the installed `ip-rule(8)` DESCRIPTION documents ordered RPDB rules with source/destination/incoming-interface/tos/fwmark selectors before table actions. Table priority, route types and selectors matter. Even existing destination-only route-get describes only that lookup context, not every possible marked/source/interface-selected packet. Any broader claimed equivalence needs an explicitly supported rule/selector model and validation against kernel results. No three-call LPM replacement is approved by this proposal.

Proposed cadence: one bounded combined verification on each serving Step and before enabling a new Apply; an independently scoped retained-topology check on each blocked Step where an acknowledged expectation exists. Reuse the same nft/TC snapshot where its generation and read lifetime match; observations publish that read's original timestamp instead of doing unbudgeted extra reads or refreshing old timestamps. All required source/topology reads share the enclosing pass deadline and the existing read budget; a timeout leaves forwarding closed. Coalescing reads is a proposal, not an implemented cost reduction.

The old `<0.1ms`, `2–4ms` and `15–25ms` estimates were **not measured** and are withdrawn. `node/agent/followup21_netlab_test.go:165–189` logs read/Step/topology timing; it does not assert a universal 150 ms bound. D-085's historical goals are not a universal measured latency bound. The earlier consumer record reports 52.6 ms added per serving Step (`docs/ROADMAP.md:158`); that historical measurement is not a cost measurement for this proposal or a replacement for the current context bounds. Before adoption, measure combined read latency and Step-to-withdraw latency across recorded prefix counts, both architectures, clean/foreign-TC/missing-route cases, and every supported RPDB selector configuration. Retain every attempt, timeout and subprocess count. Choose sample sizes and acceptance bounds before measurement; no new performance result is supplied here.
