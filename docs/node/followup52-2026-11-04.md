### Verdict and actual call sequence

`fvpn-agent run` calls Boot then repeatedly Step (`node/agent/cmd/fvpn-agent/main.go:121`,
`node/agent/engine.go:605–642`). `once` calls Boot and exactly one Step, then
Close (`cmd/fvpn-agent/main.go:120–136`). A sequence of direct Steps faithfully
models run's state transitions; repeating once starts a new Engine and does not
preserve the process-local containment or recovery opportunity.

Step refreshes the meter before evaluation/enforcement, performs generation
catch-up after enforcement, refreshes the closed recovery's decision, then
observes and flushes (`engine.go:780–804`). Its deferred final audit can also
observe/flush (`serving.go:184–203`). The bypass tests only armed/unbound at
`observe.go:39`; binding additionally tests engine eligibility, report generation,
readiness, kernel backend, null peer, awaiting grants, internet-only success,
no failed meter check, and no isolation/baseline/meter error
(`recovery_renewal.go:16–61`). The two predicates disagree.

### A — isolation error: persistent latch reachable in run; pending revoke transient

A real enforcement path can return an isolation error with quarantine evidence:
when a prior kernel quarantine marker survives restart, Apply verifies/reopens
the quarantined link and can fail isolation verification or release
(`node/enforce/apply.go:231–251`, `node/enforce/quarantine.go:167–183`). Boot can
refuse adoption before reading that path and install a baseline
(`node/agent/restart.go:18–27`, `engine.go:554–575`); the subsequent Apply can
therefore be the first containment event in this process. Its failure calls
`recordApplyQuarantine` (`engine.go:1340–1353`), which sets the first evidence
code from the CheckError and retains the quarantine (`quarantine.go:94–106`).
A plain isolation failure without quarantine does **not** establish this latch.

Next run Step, after topology repair, can receive a matching empty lease while
the Apply failure is retained. `enforce` clears the error only in its candidate
input, builds a deny-all recovery, verifies Apply and topology, then clears the
active error and arms a fresh recovery (`engine.go:1133–1143, 1361–1399`). It
does not clear the historical containment. `attachContainment` carries its
isolation error on every report (`quarantine.go:175–210`), so binding refuses it
(`recovery_renewal.go:52–55`). `retainClosedRecovery` does not reject historical
containment (`recovery.go:30–58`). With fresh matching empty leases, valid policy,
healthy local gates and an observation outage, the armed/unbound state persists
across run Steps. Ordinary D-067 renewal continues; D-157's early renewal never
opens. Member forwarding remains denied. The historical isolation code survives
until process replacement or a subsequent containment event rewrites its code
(`quarantine.go:27–31`); a populated lease plus verified serving Apply also ends
the closed recovery. Lease/policy expiry or another failed safety gate takes the
baseline. An outage limited to observations can therefore sustain the flood for
more than 32 intervals. There is no equivalent persistent sequence in one CLI
once invocation: creating the Apply latch and then recovering requires two Steps;
restarting once loses the latch. Boot's rejected-adoption quarantine retains a
foreign-tc code, not this Apply isolation latch (`serving.go:150–175`).

Pending revoke is another isolation error source (`decide.go:292–300`). A verified
closed Apply can retain failed conntrack deletions, clear applyError, and arm the
recovery (`engine.go:1335–1339, 1386–1414`). This is reachable in run and in once
when Boot retained an adoption quarantine error and Step obtains provisional or
stale authorization. It lasts until the next enforcement pass: pending revokes
prevent retention (`recovery.go:33`), so baseline disarms the opportunity
(`engine.go:1145–1158, 1055–1057`); the conntrack retry bound can withdraw it even
in the recovery Step (`engine.go:1400–1408`). It does not create a persistent
unchanged-state flood through complete Steps.

r31 A (`review_r31_test.go:17–31, 50–113` on r31) supplies the isolation/quarantine
Apply result through a fake plane, executes the failure and recovery Steps, then
calls observe alone for 31 intervals and finally Step. Its agent state is
reachable as above, but the isolated observe loop omits intervening lease,
meter and policy refreshes. Our full-Step proof must keep authorization fresh
and verify retention, unchanged state and capacity throughout the outage.

### B — failed meter: constructed armed state is unreachable at normal observation

`readMeter` copies meter health into `meterFailed` (`usage.go:356–392`) before
`evaluate` and `enforce` (`engine.go:784–789`). `Decide` adds meter_path_invalid
(`decide.go:149–150`); recoveryDecision preserves that input while clearing only
bindings/grants and aligning generation (`recovery.go:14–24`). Consequently no
closed Apply can start with a failed meter. An existing closed recovery also
fails retention's recoveryDecision (`recovery.go:37–39`) and baseline clears both
held and armed before observe (`engine.go:1145–1158, 1055–1057`). Neither run nor
once can observe the persistent armed/failed-meter combination via normal Steps.
A real later meter failure is reachable, but its report belongs to withdrawal,
not a retained closed recovery. Forwarding stays off until meter health and all
ordinary authorization/Apply gates recover; no D-157 exception is armed.

r31 B directly resets `closedRecoveryRenewal`, assigns `meterFailed`, recomputes
the decision, and loops observe without enforce (`review_r31_test.go:115–159`).
It proves the helper predicate defect, not full-Step reachability. Preserve its
assertions and fix defensively because using the exact existing binding predicate
for the bypass is narrow and changes no safety or renewal eligibility rule.

### C — stale lease reachable for one pass; zero bindings are not an independent closed gate

After a failed Apply/live read, desired generation can advance while both
pre-enforcement and post-enforcement renewals fail. Recovery uses a copied,
generation-aligned deny-all candidate; it does not rewrite the signed lease
(`recovery.go:18–24`, `engine.go:1133–1143`). The successful Apply arms recovery
at the new applied generation (`engine.go:1386–1399`). Failed catch-up leaves the
old lease (`sync.go:256–275`), so binding fails eligibility and the report says
policy_missing (`recovery_renewal.go:22`, `decide.go:185–209`). This can occur in
run; once can reach it when Boot keeps an adoption quarantine error and its one
Step receives an older-generation lease (Boot otherwise starts leaseFresh false:
`engine.go:544, 567–575`; adoption verification: `restart.go:96`).

This armed state lasts to the next enforcement, not every interval of an outage.
If catch-up succeeds with empty grants, retention and binding can proceed; if
still stale, `grantsProvisional` is false (`decide.go:550–554`), retention refuses,
and baseline disarms. A populated matching lease requires a verified serving
Apply. Retry-After cannot authorize forwarding or extend a signed lease.

With **no device bindings**, a stale-lease recovery can likewise occur, but a
same-generation empty desired/lease pair is an ordinary empty model, with no
awaiting_member_grants condition (`decide.go:227–244, 259–262`). There is no
`no_active_members` reason in this implementation. Zero bindings alone cannot
trigger closed recovery: `enforce` requires stale generation or provisional
grants (`engine.go:1138`), and provisional grants require bindings
(`decide.go:554`). If desired bindings disappear after an earlier closed Apply,
ordinary enforcement either installs the new empty model or takes baseline;
it cannot retain the previous closed opportunity. Thus the review's independent
zero-binding persistent case is unreachable. A stale zero-binding recovery is
transient and never binds; after catch-up its empty verified model contains no
member admissions.

r31 C uses real failure/recovery Steps for the stale-lease initial state, then
31 direct observes with no intervening enforcement (`review_r31_test.go:161–208`).
The initial state is reachable; that persistent observe-only history is not a
run/once history. The shared predicate still fixes its narrowly constructed
case without modifying retention, baseline or binding rules.

### Unchanged observation state can become bindable again

The observation fingerprint excludes recovery identity and bound report ID
(`observe.go:382–415`). A full outbox can suppress an intermediate failure, then
partial drain allows a second clean closed Apply at the same generation/state.
It arms a new opportunity and resets lastObs, while an older identical report
remains pending (`engine.go:1386–1389`). #470's full-Step proof pins this exact
history (`followup51_test.go:361–415`). That new recovery must queue and bind its
own report immediately; acceptance of the older report is insufficient. A stale
lease catching up normally changes policy_missing to awaiting_member_grants;
that is a state transition and also must queue without waiting for the interval.
No timestamp or semantic fingerprint should be expanded just to hide the defect.
