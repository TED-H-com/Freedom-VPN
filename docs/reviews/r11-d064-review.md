## What Held

- **`D-061` resolver credentials file hardening (`node/agent/dnsconfig.go`, `internal/dnspolicy`):** `loadResolverCredentials` opens with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, validates `fstat` on the open descriptor (`regular file`, `mode 0600`, `uid 0`, `gid 0`, `nlink == 1`, `size <= 4096`), caps reads with `LimitReader`, rejects unknown JSON fields and trailing tokens, and swaps credentials atomically on `SIGHUP` while keeping the last valid credential set on reload failure. `internal/dnspolicy` rejects inline credentials in `resolver_document` and raw config, and `node/dns/client.go` redacts error bodies and suppresses redirects.
- **Same-process single-execution and cleanup fail-closed latch (`node/agent/probeexc.go`):** Within a single running agent process, `e.probeChallenge` records the challenge identity before `ApplyProbeModel` is called, preventing a second install for the same challenge in that process. When probe cleanup fails, `baselineOK` and `serving` are cleared, `e.probe` is forced to `"probe_clear_failed"`, and `answerHealth` refuses to attest `passed`.
- **Kernel-enforced `enforce` set and chain invariants (`node/enforce/render_nft.go`, `node/enforce/verify.go`):** `@probe_v4` and `@probe_dst_v4` reject CIDR prefix objects, port ranges, and `max(timeout, expires) > 300s`, and `probe_forward` / `probe_input` remain separated from `@allowed_v4` and member usage counters (`probe_up` / `probe_down`).
- **Post-result observation authority (`internal/fleetupdate/serving.go`):** Once an incarnation has at least one accepted `update_results` row (`ack->>'accepted' = 'true'`), heartbeats cannot overwrite `nodes.current_release_id` or `nodes.last_good_release_id`, and a disagreeing heartbeat keeps `UpdateTarget.unconfirmed = true` without advancing `last_update_generation`.

## Detailed Review Notes

### 1. High (H-1) — Probe cleanup puts member forwarding back while the updater holds the lock (`#162`)

- **Location:** `node/agent/probeexc.go` (`withProbeException`, `installProbeException`, `applyProbeModel`), `node/agent/plane.go` (`ApplyProbeModel`).
- **Mechanism:** Under `#150`, `installProbeException` captured `model := e.servingModel` when `e.serving && e.servingModel != nil`, and called `e.plane.ApplyProbeModel(ctx, model)` without checking `/var/lib/vpn-node/update.lock`. When `fvpn-updater` started an update on a serving node, acquired `update.lock`, installed the fail-closed baseline, and wrote `health-challenge.json` with a synthetic `probe`, the running agent's next step installed `servingModel` + `Probe` and then cleaned up by re-applying `servingModel` (`clean.Probe = nil`), restoring `@allowed_v4` member forwarding and `e.serving = true` while the updater still held `update.lock`.
- **Proof:** `TestReviewR11_ServingProbeIgnoresUpdateLock` (`node/agent/review_r11_d064_test.go`).
- **Resolution on `main` (`#162`):** Amended `D-064` in `node/agent/probeexc.go` (`updateLockHeld`, `installProbeException`, `baselineProbeModel`) and `node/agent/plane.go` (`BaselineModel` / `ApplyBaselineModel`): the probe exception is installed only while another process holds `update.lock` (`nodelock.TryAcquire` returns `nodelock.ErrBusy`; `updateLockHeld` never blocks or keeps the lock) and a live `health-challenge.json` names this process and matches `Same`. Both installation and removal use `ApplyBaselineModel`: if the agent was serving (`e.serving || e.servingModel != nil`), `installProbeException` first calls `e.withdraw(ctx)` to clear member forwarding, and both install and cleanup render only the baseline model (zero member bindings).

### 2. Medium (M-1) — Any same-euid writer can open the probe hole the challenge file authorizes (`#156`, `#162`)

- **Location:** `node/agent/probeexc.go` (`withProbeException`, `challengeProbe`), `node/enforce/verify.go` (`verifyProbeChains`, `verifyResolverSet`).
- **Mechanism:** Because `installProbeException` did not check that another process held `update.lock`, any same-euid writer able to place `health-challenge.json` in `journal_dir` could trigger a `300s` probe hole when no update was running. In addition, `challengeProbe` checked `dns.resolvers` admin ports on node-local destinations before dry-render rather than refusing all ports on node-local addresses (`datapath.snat` and `host_v4`), and `verifyProbeChains` in `node/enforce/verify.go` did not verify that the optional probe DNS carve-out consisted of at most one TCP and one UDP port-53 rule to `@resolver_v4`.
- **Proof:** `TestReviewR11_SameUIDChallengeOpensProbeHole` (`node/agent/review_r11_d064_test.go`).
- **Resolution on `main` (`#156`, `#162`):** In `#162`, `withProbeException` requires `updateLockHeld()` (`nodelock.ErrBusy` from another process), and `challengeProbe` (`nodeLocal`) refuses any destination matching `datapath.snat` or any discovered `host_v4` address on any port before touching the plane, alongside every `enforce.SpecDeniedV4()` prefix. In `#156`, `verifyProbeChains` and `verifyResolverSet` in `node/enforce/verify.go` verify that a probe with `ResolverDNS` has at most one TCP and one UDP accept rule from `@probe_v4` to `@resolver_v4` port 53 (`iif` member ingress, `oif` uplink) and that `@resolver_v4` matches the exact configured resolver IPv4 set (`ISOLATION_POLICY_INVALID` on any wider rule).

### 3. Medium (M-2) — Issuer accepts special-purpose destinations and private sources, and has no node, control, or resolver address (`#154`, `#156`)

- **Location:** `node/enforce/prefixes.go` (`SpecDeniedV4`), `node/updater/probe.go` (`validateProbePeer`), `node/updater/probe_addresses.go` (`probeEnvironment`, `readProbeAgentConfig`, `Engine.challengeProbe`).
- **Mechanism:** `SpecDeniedV4()` omitted `192.88.99.0/24` (deprecated 6to4 relay anycast, RFC 7526, `Globally Reachable = False` in the IANA IPv4 Special-Purpose Address Registry). On the issuer side, `updater.json` did not load `agent.json` or live host interface addresses, so `validateProbePeer` could not reject a node's own interface IPv4 address (as `source_v4` or destination), the `control_url` / `result_url` host addresses, or configured `dns.resolvers` addresses.
- **Proof:** `TestReviewR11_IssuerSpecialPurposeDestinations` (`node/updater/review_r11_d063_test.go`).
- **Resolution on `main` (`#154`, `#156`):** In `#156`, `SpecDeniedV4()` in `node/enforce/prefixes.go` includes `192.88.99.0/24` so every IANA IPv4 Special-Purpose Address Registry block with `Globally Reachable != True` plus multicast `224.0.0.0/4` is denied (while globally reachable `192.31.196.0/24`, `192.52.193.0/24`, and `192.175.48.0/24` remain allowed). In `#154`, `node/updater` (`probe.go`, `probe_addresses.go`, `host.go`) adds `agent_config` (default `/etc/vpn-node/agent.json`, regular file `<= 1 MiB`, resolver credentials never opened) and validates `probe_peer` at `LoadConfig`, `Config.Engine()`, and every `issueChallenge` (`Engine.challengeProbe`) against live IPv4 global-unicast interface addresses (`net.InterfaceAddrs`), `control_url`/`result_url` addresses, and `dns.resolvers[].dns_addr`/`admin_url` hosts under a shared `2s` DNS deadline; if an input is unavailable or forbidden at issuance, `challengeProbe` omits `probe` from `health-challenge.json` and logs `"health challenge probe omitted"` once per fixed `probeRefusal` class per `Engine`.

### 4. Medium (M-3) — `trustedNow` installs a probe that wall time will not answer (`#162`)

- **Location:** `node/agent/probeexc.go` (`installProbeException`), `node/agent/attest.go` (`answerHealth`).
- **Mechanism:** `installProbeException` evaluated the challenge window (`issued_at < now < expires_at`) using `e.trustedNow(mono)`, which advances monotonically from a signed control timestamp when wall time is behind, whereas `answerHealth` checked `wall.After(ch.IssuedAt) && wall.Before(ch.ExpiresAt)` using `e.clock.Wall()`. Under a forward-skewed `trustedNow` relative to wall time, the agent installed and removed the kernel probe exception for a challenge that `answerHealth` then refused to answer.
- **Proof:** `TestReviewR11_TrustedNowInstallsWhenWallRefusesAnswer` (`node/agent/review_r11_d064_test.go`).
- **Resolution on `main` (`#162`):** Both `installProbeException` (`node/agent/probeexc.go`) and `answerHealth` (`node/agent/attest.go`) validate the challenge window with `now := e.trustedNow(mono)`.

### 5. Medium (M-4) — A new process reinstalls the same challenge, and `ProbeRemain` 0 extends it past the issuance (`#162`)

- **Location:** `node/agent/probeexc.go` (`probeChallenge`, `probeIssuance`, `installProbeException`), `node/internal/agentstore/store.go` (`Meta`, `SetMeta`).
- **Mechanism:** Because `e.probeChallenge` lived only in memory, a restarted `fvpn-agent` process had `e.probeChallenge == nil` and `plane.ProbeRemain() == 0` after the previous process's `defer` cleared the kernel sets. If the same `health-challenge.json` was still present (and wall clock stepped back inside the window), the new process reinstalled the same challenge with a fresh `TimeoutCeilSeconds`, extending total probe lifetime past `expires_at` and `issued_at + 300s`.
- **Proof:** `TestReviewR11_RestartRemainCapAndAnomalyExtension` (`node/agent/review_r11_d064_test.go`).
- **Resolution on `main` (`#162`):** `installProbeException` persists `probe_issuance` (`{nonce, hash, issued_at, deadline_ns, cleared}`, where `hash` is the canonical JSON SHA-256 digest of `ch.Probe` with no destination list stored, `SEC02`) in `agentstore` (`Meta` / `SetMeta`) before calling `ApplyBaselineModel`, and marks `cleared = true` on cleanup. A cleared issuance is never reinstalled by a later process; an uncleared issuance on the same boot caps the remaining window to `min(old.Deadline - mono, expires_at - trustedNow)`.

### 6. Medium (M-5) — Zero-binding publication leaves the NetBird route up when the first binding arrives (`#160`)

- **Location:** `internal/nodes/publication_evidence.go`, `internal/nodes/publication_gate.go`, `internal/exits/publication_gate.go`, `internal/exits/exits.go`.
- **Mechanism:** Under `#148`, a zero-binding published node (`device_bindings: []`) could complete `node.publish` and attach its NetBird exit route with `lease`, `qos`, and `source_binding` in `not_run`. When the first member device was subsequently authorized and a populated desired-state generation (`device_bindings` non-empty) was compiled, nothing withdrew the NetBird route or gated delivery while the node's observation was still on the zero-binding generation or had not yet reported passing `lease`, `qos`, and `source_binding`.
- **Proof:** `TestReviewR11_ZeroBindingRouteBeforeFirstBindingChecks` (`internal/nodes/review_r11_publication_test.go`).
- **Resolution on `main` (`#160`):** `RecordPublicationAttachmentTx` (`internal/nodes/publication_gate.go`) records `publication_attachment_basis` (`empty_exception` vs. `populated_verified`) in `operations.observed_refs`. When the latest succeeded `node.publish` used `empty_exception` and the first populated generation is compiled, `QueuePublicationGateTx` queues a `node.publish` operation under `system:publication-gate`. While the node's observation is on an older generation (`stale_generation`) or lacks passing `lease`, `qos`, and `source_binding` (`serving_checks_unconfirmed`), `failGatedPublish` (`internal/exits/publication_gate.go`) withdraws the NetBird route and reads back its withdrawal under the per-node advisory lock, sets `exits.publication_observed = 'withdrawn'` (cause `member_forwarding_unconfirmed`, D-029 `node.publish` audit), and `CheckPublicationDelivery` withholds the populated desired-state envelope (`503 DEPENDENCY_UNAVAILABLE`) until withdrawal is confirmed. Once the agent acknowledges the populated generation with passing `lease`, `qos`, and `source_binding`, a recovery `node.publish` operation re-attaches and reads back the route, setting `publication_observed = 'active'` and `populated_verified`. A `populated_verified` attachment is never withdrawn by this mechanism and never blocks desired-state delivery.

### 7. Medium (M-6) — Heartbeats move the serving release to a release that was never a job target (`#155`)

- **Location:** `internal/fleetupdate/serving.go` (`Service.observeTx`, `auditUnexpectedRelease`).
- **Mechanism:** Under `#140`, before a node incarnation had its first accepted `update_results` row, `observeTx` allowed a heartbeat to seed `nodes.current_release_id` and `nodes.last_good_release_id` when those columns were `NULL`, without checking whether the reported release was the active job's `target_release_id` or already recorded on `nodes`. A compromised or misreporting pre-result node could seed an arbitrary serving release ID as both `current_release_id` and `last_good_release_id`.
- **Proof:** `TestReviewR11_PreResultHeartbeatSeedsUntargetedRelease` (`internal/fleetupdate/review_r11_d064_integration_test.go`).
- **Resolution on `main` (`#155`):** In `internal/fleetupdate/serving.go` (`observeTx`, `auditUnexpectedRelease`), before the incarnation's first accepted result, a heartbeat may seed `nodes.current_release_id` only when the reported release equals the current job's `targetRelease` (for the same incarnation) or a release already recorded in `nodes.current_release_id` or `nodes.last_good_release_id`. Heartbeats never establish `nodes.last_good_release_id` (only accepted results do), and `recovery_required` is derived from the recorded `last_good_release_id`. Any other release in `current_release_id` or `last_good_release_id` is ignored for the version columns, withholds confirmation (`unconfirmed = true`), and appends at most one D-029 audit event `update_observation.unexpected_release` per distinct `(job_id, release_id)`.

### 8. Low (L-1) — `RenewLease` returns inside `Retry-After`, and the agent tries again on the next call (`#162`)

- **Location:** `node/internal/controlclient/api.go` (`Client.RenewLease`, `Client.RenewLeaseOnce`), `node/agent/sync.go` (`Engine.syncLease`, `Engine.renewAppliedLease`).
- **Mechanism:** `controlclient.Client.RenewLease` parsed `Retry-After` onto `StatusError` on HTTP `429` without waiting, and when `syncLease` received `429` before applying a new generation, `renewAppliedLease` in the same `Step` immediately issued a second `POST /api/v1/agent/leases/renew` inside the `Retry-After` window.
- **Proof:** `TestReviewR11_RenewLeaseReturnsBeforeRetryAfter` (`node/internal/controlclient/review_r11_lease_test.go`).
- **Resolution on `main` (`#162`):** `controlclient.Client.RenewLease` waits out `StatusError.RetryAfter` (or context cancellation) before returning the `429` error without issuing a second request, while `Client.RenewLeaseOnce` returns `StatusError` (`RetryAfter`, `RetryAt`) immediately so the agent can record `e.leaseRetryAt = mono + retryAfter` (`e.leaseAttempted = true`, at most one renewal HTTP call per step) and report `lease` check `RATE_LIMITED` (`"Lease renewal is waiting for Retry-After."`) without blocking heartbeats or observations.
