#### H-1: Unsettled generation transitions and failed `handoff` `FinalSample` allow a rebinding `Apply` to misattribute bytes to the wrong member and subscription revision

- **Severity:** High
- **File:line:**
  - `node/agent/engine.go:665-671` (`Step` only gates on `e.retainedPending`)
  - `node/agent/engine.go:713, 728, 743` (`syncLease` renews lease before `syncDesired`, allowing `Decide` to approve a new generation in the same `Step` without a baseline `handoff`)
  - `node/agent/engine.go:1187-1265` (`enforce` applies the new generation without settling or checkpointing the previous serving generation, overwrites `e.meterSnap` at line 1243 and `retained_applied` at line 1265, and pokes `m.wake` asynchronously at line 1255)
  - `node/agent/usage.go:309-328, 350-367, 373-433` (`readMeter` clears `e.usagePersist = false` at line 327; `handoff` leaves `e.retainedPending = false` and `e.finalDone = false` when `FinalSample` fails at line 400; `enforce` skips `PrepareSampling`/`ResumeSampling` when `!e.finalDone` at line 1205)

- **Violated invariant:**
  - `docs/node/followup38-r21-attribution-and-boot-2026-11-03.md` (**Design / Restart Attribution And Final-Sample Settlement**):
    - *"A rebinding Apply never runs while a retained delta is unsettled."*
    - *"Crash after the write, before the first poked sample: retained matches desired; both hold the generation that Apply just installed."*
  - `docs/spec/PROJECT_SPEC.zh-TW.md §4 MTR01, MTR02, MTR03, §10.4` (usage increments must be attributed to the member/subscription revision that actually carried the bytes, or recorded as an explicit gap when attribution is ambiguous; never silently billed to another member as `UsageQualityComplete`).
- **Attack / failure trace:**
  - **Trace A (direct generation transition `Gen 3 -> Gen 4` during `Step` lease renewal or background sample delay, followed by crash after `retained_applied` write or next sample):**
    1. Node serves Generation 2 (`Device A -> (M0, rev 1)`). Either:
       - Process 1 restarts and adopts Generation 2 (`adoptStoredServing` sets `e.leaseRefreshPending = true`), or
       - Process 1 is within `renewLead` of its lease expiry (`syncLease` at `engine.go:713` renews the lease before `syncDesired` at `engine.go:728`).
    2. Central publishes Generation 3, which adds `Device B -> (Member M1, rev 2)`. In `Step`, `syncLease` acquires a fresh lease (`Lease.ConfigGeneration = 3`), `syncDesired` fetches Generation 3, and `enforce` runs `e.plane.Apply(Gen 3)`, updates `e.meterSnap` and `retained_applied` to Generation 3, and pokes `m.wake` asynchronously (`usage.go:356` non-blocking `select`).
    3. Kernel nftables counters for `Device B` accumulate `4096 B` of traffic while `Device B` is bound to `Member M1 (rev 2)`. Before the asynchronous background sample for Generation 3 commits to `usage.db` (`head.Counters` still has no entry for `Device B`, `hadOld == false`), a second `Step` runs when the lease is due for renewal (or forced refresh).
    4. Central has published Generation 4, which rebinds `Device B -> (Member M2, rev 3)`. `syncLease` renews the lease for Generation 4; `syncDesired` fetches Generation 4; `Decide` returns `Serve: true` directly for Generation 4 without ever going through `handoff`.
    5. `enforce` (`engine.go:1187-1265`) does **not** sample or settle Generation 3 before calling `e.plane.Apply(Gen 4)` (which preserves the per-device kernel counter for `Device B`), immediately overwrites `e.meterSnap` (`engine.go:1243`) and `retained_applied` in `agent.db` (`engine.go:1265`) with Generation 4 (`Device B -> (M2, rev 3)`), and pokes `m.wake`.
    6. **Even in the exact crash window claimed safe by the follow-up 38 design note (*"Crash after the [`retained_applied`] write, before the first poked sample"*):** Process 1 crashes right after `SetMeta("retained_applied", Gen 4)` and before the poked sample runs; Process 2 starts on `Boot`, refuses adoption, runs `captureRestartBindings` (which sees `retained == Gen 4` and `desired == Gen 4`, so `commonUsageBindings` retains `Device B -> (M2, rev 3)`), and `settleRetainedUsage` -> `FinalSample` sees `hadOld == false` for `Device B` in `head.Counters` and records a **`4096 B` `UsageQualityComplete` increment billed to `Member M2 (rev 3)`** for traffic generated by `Member M1 (rev 2)` under Generation 3. (The exact same misattribution also occurs without a crash as soon as the poked sample runs.)
  - **Trace B (failed `handoff` `FinalSample` during runtime withdrawal followed by lease renewal + rebinding `Apply`):**
    1. Node serves Generation 2 (`Device A -> (M0, rev 1)`, `Device B -> (M1, rev 2)`), and `Device B` accumulates `4096 B` in kernel counters.
    2. Central publishes Generation 3 (`Device B -> (M2, rev 3)`). `Step` fetches Generation 3 while the lease is still on Generation 2 (`lease_generation_mismatch`), so `enforce` calls `e.handoff(ctx)`.

    5. On the next `Step`, `e.retainedPending` is `false`, so `Step` does not call `settleRetainedUsage`. If `syncLease` is in its renewal window (or after `leaseRefreshPending`), `syncLease` at `engine.go:713` renews the lease to Generation 3, `Decide` returns `Serve: true`, `e.readMeter(ctx)` at `engine.go:753` (`usage.go:327`) **unconditionally resets `e.usagePersist = false`**, and `enforce` runs with `e.finalDone == false`:
       - Because `!e.finalDone`, `enforce` skips `PrepareSampling` (`engine.go:1205`),
       - Calls `e.plane.Apply(Gen 3)` while Generation 2's `4096 B` delta is still unsettled in the kernel counters,
       - Overwrites `e.meterSnap` (`engine.go:1243`) and `retained_applied` (`engine.go:1265`) with Generation 3 (`Device B -> (M2, rev 3)`),
       - Pokes `m.wake` (or on `FinalSample` / next sample), which attributes the unsettled `4096 B` from `Member M1 (rev 2)` to **`Member M2 (rev 3)` as `UsageQualityComplete`**.
       - Furthermore, if `FinalSample` at step 4 failed with a non-`ErrHold` error (so `m.paused` remained `true`), skipping `PrepareSampling`/`ResumeSampling` (`!e.finalDone`) causes the node to re-enter `e.serving = true` with periodic metering permanently paused!

#### H-2: `captureRestartBindings` misidentifies candidate generations on refused adoption, turning unambiguous single-binding traffic (and even 100% of node traffic) into false `mapping conflict` gaps across 5 crash windows

- **Severity:** High
- **File:line:**
  - `node/agent/restart_usage.go:17-93` (`captureRestartBindings` and `commonUsageBindings`)
  - `node/agent/engine.go:763-772` (`saveDesired` overwrites `desired` in `agent.db` before `Decide` and before `e.plane.Apply`)
  - `node/agent/engine.go:1265` (`SetMeta("retained_applied")` runs after `e.plane.Apply`, carries no `BootID`/`EpochID`, and is not cleared/marked on epoch close)
- **Violated invariant:**
  - `docs/node/followup38-r21-attribution-and-boot-2026-11-03.md` (**Problem 1 & Design**):
    - *"When retained_applied and desired match for a device, that device's retained counters are attributed cleanly. When a device's (MemberID, SubscriptionRevision) differs between the two, the device is omitted from the retained binding map; FinalSample sees an unbound non-zero delta for that device, records a gap, and closes the epoch."*
    - *"Pure single-generation traffic is never converted into a gap by an unapplied desired fetch."*
  - `docs/spec/PROJECT_SPEC.zh-TW.md §4 MTR01, MTR02` (accurate per-device usage accounting without losing valid single-generation traffic on restart).
- **Attack / failure trace:**
  `captureRestartBindings` (`restart_usage.go:17-43`) unconditionally intersects `e.appliedModel.Bindings` (`retained_applied`) with `desiredBindings` (requiring exact presence and match in **both** maps via `commonUsageBindings` at lines 69-93 whenever `hasDesired` is true). That logic fails in five distinct crash scenarios:
  1. **Crash after `saveDesired(Gen 4)`, before `e.plane.Apply(Gen 4)` (`gen == retained.Generation > 0`):**
     - Process 1 is serving Generation 3 (`Device B -> (M1, rev 2)`), fetches Generation 4 (`Device B -> (M2, rev 3)`), persists `desired` (Gen 4) at `engine.go:768`, and crashes before `e.plane.Apply` (or while `Decide` withholds serving waiting for a Gen 4 lease).
     - The live kernel table still has `RestartGeneration == 3` (`gen == e.appliedModel.Generation`). Generation 4 was **never** applied to the kernel.
     - On Process 2 `Boot`, if adoption is refused (e.g., lease expired during the crash or `SIGTERM`), `captureRestartBindings` checks `gen == desiredGen` (`3 == 4`, false), falls through to `commonUsageBindings(retained.Bindings, desiredBindings)`, drops `Device B`, and turns 100% of `Device B`'s pure Generation 3 delta into a `mapping conflict` gap.
  2. **Crash after saving an `unpublished` / ` draining` / non-servable `desired` (`PublicationIntent == unpublished`):**
     - Process 1 serves Generation 2 (`Device A -> (M1, rev 1)`). Central returns an `unpublished` desired state (Generation 3, `PublicationIntent: "unpublished"`, `DeviceBindings: []`), which `saveDesired` writes to `agent.db`.
     - Even if Process 1 then calls `handoff` (setting kernel `RestartGeneration = 0`, baseline) and crashes before `FinalSample` completes, an `unpublished` desired state can **never** pass `Decide` or be passed to `e.plane.Apply`.
     - On Process 2 `Boot`, `gen == 0`, so `captureRestartBindings` intersects `retained.Bindings` with `desiredBindings == []`, returning `nil` and wiping **every device's retained traffic on the entire node** into a gap.
  3. **Device removed or newly added in `desired` (`commonUsageBindings` requires membership in both maps):**
     - In `node/enforce/render_nft.go:59-64, 170-179`, a generation that omits a device renders **no** nftables counter rules (`u_<D>` / `d_<D>`) for that device (`Baseline` and `Apply` preserve existing kernel counter objects without incrementing them for omitted devices).
     - Therefore:
       - If `Device B` was in `retained` (Gen 2) and removed in `desired` (Gen 3), any retained counter delta for `Device B` could only have accumulated under Gen 2's binding.
       - Conversely, if `Device C` was absent before Gen 3 (`head.Counters["C"]` absent) and newly added in `desired` (Gen 3), any positive counter for `Device C` could only have accumulated after `plane.Apply(Gen 3)` under Gen 3's binding.
     - Because `commonUsageBindings` requires `ok := b[id]` in **both** `retained` and `desired`, both `Device B` and `Device C` are dropped from the binding map and their unambiguous single-binding traffic is turned into a `mapping conflict` gap.
  4. **Stale `retained_applied` from an already-closed epoch (or prior boot):**
     - `retained_applied` in `agent.db` stores only `enforce.Model` with no `BootID`, `EpochID`, or `settled` flag, and is not updated when `handoff` / `FinalSample` closes an epoch.
     - Process 1 serves Gen 2 (`Device A -> rev 1`), withdraws to `Baseline`, and `FinalSample` closes Epoch 1 (e.g., on counter reset or gap). Later, Process 1 applies Gen 3 (`Device A -> rev 2`) in a new Epoch 2, and crashes after `e.plane.Apply(Gen 3)` (and even after `Baseline` in `handoff`, so `gen == 0`) before `SetMeta("retained_applied", Gen 3)` is written.
     - On Process 2 `Boot`, `retained_applied` still holds Gen 2 from closed Epoch 1 while `desired` holds Gen 3. `captureRestartBindings` intersects Gen 2 (`rev 1`) with Gen 3 (`rev 2`), falsely diagnosing a conflict and turning Gen 3's traffic into a gap.
  5. **First-ever `Apply` on a node crashes before `SetMeta("retained_applied")`:**
     - On a node that has never written `retained_applied` (`e.appliedModel == nil`), Process 1 fetches `desired` (Gen 2), runs `e.plane.Apply(Gen 2)`, accumulates traffic, and crashes before `SetMeta("retained_applied", Gen 2)` at `engine.go:1265`.
     - On Process 2 `Boot`, `captureRestartBindings` hits `if e.appliedModel == nil { return }` at line 19 — even though the live kernel table has `RestartGeneration == 2 == restartDesired.ConfigGeneration` — leaving `e.retainedPending = false` and `meterSnap = nil` so `ensureUsage` records a `mapping conflict` gap for all traffic.
- **Proof:**
  - Test: `TestR22_H2_CaptureRestartBindingsFalseGapsAcrossCrashWindows` (5 subtests) in `node/agent/review_r22_test.go`
  - Output against `31862b3a`:

- **Smallest complete fix:**
  1. Write a pre-apply intent record (e.g., `pending_apply` or `retained_applied` with `{boot_id, open_epoch, settled, applied_model, candidate_model}`) in `agent.db` **immediately before** `e.plane.Apply(ctx, d.Model)` (after `Decide` has already proved `d.Serve == true`), and update it to settled `{applied_model: d.Model, candidate_model: nil}` immediately after `e.plane.Apply` succeeds (and mark `settled = true` when `FinalSample` closes/settles the generation).
  2. In `captureRestartBindings`:
     - If `gen > 0` and `gen == retained.Generation`, use `retained.Bindings` directly (`desired` was never applied to the kernel).
     - If `retained == nil` and `gen > 0 && gen == desiredGen`, use `desiredBindings`.
     - Only treat `desired` as a candidate when it was actually eligible to be applied (or recorded in `pending_apply` for the current `boot_id`/`open_epoch`), and for devices present in only one candidate generation (where `head.Counters[dev]` has no conflicting prior binding), keep that single binding instead of requiring presence in both maps.

## 3. What held

All seven attack questions in `.agent/BRIEF.md` and all prior `r20`/`r21` findings were directly probed with adversarial tests:

1. **Attack Question 1 (Multi-generation restart window & cold-boot baseline):**
   - When Process 1 crashes *after* `e.plane.Apply(Gen 3)` and *before* `SetMeta("retained_applied", Gen 3)`, and Process 2 refuses adoption after `handoff` sets `gen == 0`, `captureRestartBindings` intersects `retained` (Gen 2) with `desired` (Gen 3), attributing unchanged devices cleanly and recording a gap + closing the epoch for rebound devices (`TestR21_H1_RestartAfterRebindingApplyAttributesRetainedCountersToOldMember`).
   - On a brand-new node (`head.OpenEpoch == uuid.Nil`, `e.retainedPending == false`) and after an unclean reboot (`head.BootID != e.bootID.String()`, `e.retainedPending == false`), `ensureUsage` clears `meterSnap` before `meter.NewContext` so baseline counters are recorded unbound (`MemberID == uuid.Nil`), and the first serving `Apply` + `SampleNow` attributes only post-`Apply` deltas without a false `mapping conflict` (`TestR22_Held_Q1_FreshInstallColdBootAndUncleanRebootBaseline`).
2. **Attack Question 2 (Held `FinalSample` across `Boot` and `Step`):**
   - When `Boot` refuses adoption and `FinalSample` returns `meter.ErrHold` because `usage.db` is at `MaxUnackedRows` (`8640`) and the uploader cannot flush, `e.retainedPending` stays `true`, and `Step` blocks `syncLease`, `syncDesired`, and `e.plane.Apply` at the top of `Step` until the uploader flushes and `settleRetainedUsage` succeeds (`TestR22_Held_Q2_Q3_HeldFinalSampleWaitsInStepAndAdoptionSuppressesProbeException/held_finalsample_blocks_step_sync_and_apply_until_settled`). *(Except when `ensureUsage` itself fails during `Boot` — see `M-1` — or when `handoff` fails `FinalSample` during `Step` — see `H-1`.)*
3. **Attack Question 3 (Boot budget split and probe exceptions):**
   - `adoptStoredServing` wraps its context with `withProbeNoInstall(ctx)` (`restart.go:47`), preventing `syncLease` / `syncDesired` from calling `plane.InstallProbeException` while holding `lockUpdate` during adoption (`TestR22_Held_Q2_Q3_HeldFinalSampleWaitsInStepAndAdoptionSuppressesProbeException/adoption_lock_does_not_trigger_probe_exception_install`).
   - `bootWithBudget` splits `bootAdoptBudget` (for `adoptStoredServing`) from `bootLocalBudget` (for `Baseline`, `ensureUsage`, `settleRetainedUsage`, `beat`, and `answerHealthOnBoot`) so a slow adoption network call cannot starve `Baseline` installation (`TestR21_M2_BootTimeoutAndSignalHandling`).
4. **Attack Question 4 (`FinalSample` epoch-close condition in `node/internal/meter/meter.go`):**
   - `SampleAndClose` (`meter.go:304-370`) closes the open epoch (`closeEpoch = true`, `nextID = uuid.Nil`, `openEpoch = uuid.Nil`, `lastMono = 0`, `lastWall = time.Time{}`) on `mapping conflict`, `counter reset`, and `monotonic clock gap`, and keeps the epoch open on a clean `UsageQualityComplete` sample so a later re-adoption or same-boot resume does not lose baseline continuity (`TestR22_Held_Q4_Q5_Q6_Q7_FinalSampleCloseAndStopBudgetAndMemberPathEvidence/finalsample_closes_epoch_on_counter_reset_and_clock_gap`).
5. **Attack Question 5 (Uploader lifecycle):**
   - On clean `Boot` with `e.retainedPending == true`, `ensureUsage` defers `up.Run` until `settleRetainedUsage` finishes `FinalSample`, avoiding SQLite lock contention between background batching and `FinalSample` before starting the background loop (`TestR22_Held_Q2_Q3_HeldFinalSampleWaitsInStepAndAdoptionSuppressesProbeException`). *(Note: `M-2` covers the edge case where `adoptStoredServing` calls `ensureUsage` before `e.retainedPending` is set.)*
6. **Attack Question 6 (Stop budget):**
   - `defaultStopTimeout` in `node/agent/cmd/fvpn-agent/main.go:27` is `15 * time.Second`, and `deploy/systemd/fvpn-agent.service` sets `TimeoutStopSec=20s` (5s headroom above `15s`), giving `Shutdown` (`Baseline` + `FinalSample` + `FlushNow` + `beat`) sufficient budget before systemd sends `SIGKILL` (`TestR22_Held_Q4_Q5_Q6_Q7_FinalSampleCloseAndStopBudgetAndMemberPathEvidence/stop_budget_constants_and_member_path_retained_across_restart`).
7. **Attack Question 7 (`r20` preservation — member path evidence across restart):**
   - `memberPath` evidence (`MemberPathVerified`, `MemberPathSummary`) is persisted in `agent.db` (`member_path` meta key) and restored on `loadRuntime`, surviving process restarts and clearing on revocation/generation mismatch (`TestR22_Held_Q4_Q5_Q6_Q7_FinalSampleCloseAndStopBudgetAndMemberPathEvidence/stop_budget_constants_and_member_path_retained_across_restart`, `TestR20_H1_RestartPreservesOrRecomputesMemberPathEvidence`).
