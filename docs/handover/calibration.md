# Parameter Calibration Guide (`docs/handover/calibration.md`)

This guide catalogs every business, policy, capacity, timing, DNS, and retention parameter that requires explicit decision or empirical calibration before and during production operations (`§4`, `§6`–`§13`, `§15`–`§17`, `§20`–`§22`).

In accordance with `AGENTS.md §1` and Decision `D-045`, parameters marked `待決策` (pending business decision) or `待實測` (needs measurement) never carry silent compiled-in production defaults. Every parameter below specifies:
- **Location**: Config file JSON key, active policy payload (`POST /api/v1/admin/policies`), or node/API field.
- **Default Status**:
  - `none`: No compiled default; startup or validation fails closed if omitted.
  - `test only`: Repository fixtures/examples supply a `TEST ONLY` placeholder that must be replaced in production.
  - `proposed`: Spec defines a `建議預設` (recommended default) implemented as a configurable parameter.
- **Spec Section**: Constraining section(s) in `docs/spec/PROJECT_SPEC.zh-TW.md`.
- **Decision Owner**: `Ted` (commercial/product/legal owner) or `core team` (engineering/operations team).

## 2. Step-by-Step Calibration Workflow (`§11.4`, `§20.2`)

### 2.1 Calibrating Per-Node Capacity Ceilings and `host_reserve_bps` (`§20.2`)

Before setting `publication_intent = "published"` on a new exit node hardware profile (`amd64` or `arm64`):
1. Measure sustained NIC throughput and CPU softirq head-room inside an isolated test or staging environment (`docs/poc/G2-netlab.md`; in the E2E lab, `Stack.StartNodeTelemetry` in `#182` samples cgroup v2 CPU/memory, process FDs, and `nf_conntrack_count` every `5s` for workload measurement only, not hardware certification).
2. Set `host_reserve_bps` in `/etc/vpn-node/agent.json` from measured host control-plane needs; it must be greater than zero. Restart `fvpn-agent.service` after changing the configuration. This is a shaping reserve, not a guarantee that all control traffic avoids congestion. Verify the node's post-restart serving checks using the [operator node procedure](operator-guide.md#32-updating-node-region-member-groups-or-capacity-patch-apiv1adminnodesnode_id).
3. Configure `capacity` on the node via `PATCH /api/v1/admin/nodes/{node_id}` (`If-Match` required) to `85%–90%` of measured sustainable WireGuard + `tc` HTB throughput so `fq_codel` controls queue delay on the node rather than dropping packets in upstream provider buffers.

### 2.2 Calibrating Fair-Use Thresholds from Shadow Mode (`§11.4`, `FUP04`)

1. Launch with `"fup_mode": "shadow"` in `/etc/fvpn/policies.json` and activate an initial `fair_use` policy revision.
2. In `shadow` mode, `fvpn-worker` computes tier transitions (`fup_member_states`) and emits audit/telemetry records, while omitting only the fair-use tier cap from node desired state (the plan rate and node per-member rate cap still apply); the control API returns `state: "normal"` (`applying: false`, `rate: null`) to members through its usage reader (`docs/policies/README.md`).
3. At the end of the first billing cycle, query the distribution of member monthly usage in PostgreSQL:
   ```sql
   SELECT
     percentile_cont(0.50) WITHIN GROUP (ORDER BY (upload_bytes + download_bytes)::double precision) AS p50_bytes,
     percentile_cont(0.90) WITHIN GROUP (ORDER BY (upload_bytes + download_bytes)::double precision) AS p90_bytes,
     percentile_cont(0.95) WITHIN GROUP (ORDER BY (upload_bytes + download_bytes)::double precision) AS p95_bytes,
     percentile_cont(0.99) WITHIN GROUP (ORDER BY (upload_bytes + download_bytes)::double precision) AS p99_bytes
   FROM usage_rollups
   WHERE granularity = 'month'
     AND period = to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM');
   ```
4. Carried gap: there is no documented read-back procedure confirming the effective mode in both running services after this restart; do not infer it from file contents or policy activation alone. Once `Ted` approves the production `threshold_bytes` and tier rates (`down_bps`, `up_bps`, `minimum_rate`), create and activate a new `fair_use` policy revision (`POST /api/v1/admin/policies` -> `POST /api/v1/admin/policies/{definition_id}/activate`) and switch `"fup_mode": "enforce"` in `/etc/fvpn/policies.json`. Restart both services with `systemctl restart fvpn-control.service fvpn-worker.service`: they copy this override into their engines at construction, so editing the file does not change a running engine. The override takes precedence over the active revision's mode, although a future `effective_at` still forces shadow mode. The existing [member/application status checks](../policies/README.md#4-shadow-vs-enforce-rollout-procedure-112-fup02) remain useful but do not establish both loaded overrides. Under `#222`, activating a `fair_use` revision (`policy.activated`) and any member tier change (`fup.member_generation_changed`) recompile desired state (`Compiler.RecompileBatch`) on every published exit carrying an affected member, and `fair_use.applying` reflects the ACK conditions in §1.3. In enforce mode with a positive generation, an unacknowledged carrying exit keeps it `true`; an acknowledged exit going offline or stale does not make it `true` again while the other ACK conditions still hold.
