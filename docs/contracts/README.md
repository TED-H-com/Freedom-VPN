# API contracts

This directory documents the Freedom VPN contracts: the HTTP API, the signed
and hashed documents, the shared vectors and the shared Go leaf packages.
The product contract is [`docs/spec/PROJECT_SPEC.zh-TW.md`](../spec/PROJECT_SPEC.zh-TW.md)
(Project Spec v1.0), cited as `§<chapter>.<section>`.

## Release trust-update document

The proposal in [PKI rotation](../pki/rotation.md#release-verification-trust) is
concrete, and `internal/signing.ReleaseUpdate`/`KeyRecord` supplies the field
names. [The schema](../../contracts/schemas/trust/release-update-envelope.schema.json)
therefore publishes its existing non-HTTP envelope without adding an endpoint:

| Signed member | Meaning |
|---|---|
| `kind` | Exactly `fvpn-release-trust-v1` |
| `revision` | Strictly increasing decimal-string uint64 |
| `keys` | Public records: `id`, `purpose=release`, base64 `public`, `state`, `not_before`, `not_after`, optional `revoked_at` |

`state` is active, retired or revoked; `revoked_at` is present iff revoked.
Verification uses purpose **release** and the **old** trust store. It must reject
bad/revoked/out-of-window known signers before accepting any advertised key.
The service also checks unique IDs/public bytes, increasing revision, ordered
validity, unchanged public bytes for old IDs, nonexpanding validity, no
retired-to-active transitions, terminal revocation, and retention of omitted
old records. Schema acceptance alone does not authorize rotation. It grants no
central or node-ca purpose and distributes no private keys.

[The signed vector](../../contracts/vectors/release-trust-update-signing.json)
uses the existing TEST ONLY release root to authorize the previously untrusted
TEST ONLY public key. Go and TypeScript reverify its signature and hash; schema
fixtures reject a wrong kind/purpose, numeric revision, private material,
malformed public key, and missing revocation timestamp.

## Conventions

These rules are enforced by tests in `contracts/` (test names in brackets).

- **Prefix and paths.** Paths are relative to the server URL `.../api/v1`.
  JSON is UTF-8. [`TestAPI01_EndpointCountIs44`]
- **IDs.** Our entity, operation and request IDs are UUIDs (`format: uuid`).
  External IDs (NetBird peer, OIDC subject, provider price) are opaque strings.
  [`TestAPI01_IDTimeAndMoneyConventions`]
- **Times.** `format: date-time` plus a pattern that requires UTC with `Z`.
  Intervals are half-open `[start, end)`. Sequence ranges (`SeqRange`) are
  inclusive, as in the §17.3 example.
- **Large integers.** Bytes, sequence numbers, generations, revisions and
  resource versions are decimal strings: `type: string`,
  `pattern: '^(0|[1-9][0-9]*)$'` (`'^[1-9][0-9]*$'` where zero is invalid,
  such as `event_seq` and `DomainRule.revision`), `maxLength: 20`, `x-go-type: decstr.U64`,
  `x-go-type-import: {path: github.com/TED-H-com/Freedom-VPN/pkg/decstr}`.
  D-056 explicitly bounds `ResolverDocumentRef.size_bytes` to the JSON integer range 1–1048576; it is the only byte-length exception. Any other field named `*_bytes`, `*_seq`, `*generation`, `*revision` or
  `resource_version` must follow it. TypeScript code holds them as strings and
  converts with `BigInt`, never `Number`. [`TestMTR03_DecimalStringConvention`]
- **Other integers** (schema versions, attempts, counts, bps rates) are JSON
  integers with explicit bounds within ±(2^53−1). No floating-point numbers.
- **Money.** `amount_minor` (int64 minor units) plus ISO 4217 `currency`.
- **Nullability and presence.** `nullable: true` is allowed on required
  members and the two optional UpdateTarget policy-evidence members (D-048). Go uses `presence.Nullable[T]` from `pkg/api/presence` (imported as
  `nullable`); its zero value is unspecified and **fails marshaling**. Use
  `NewNullNullable[T]()` for explicit null and `NewNullableWithValue(value)`
  for a value, or `SetNull`/`Set`. Inspect `IsSpecified`, `IsNull` and `Get`.
  Optional `UpdateTarget.policy_generation` and `policy_refs` use the same
  type with `omitzero`: unspecified fields are omitted, while explicit null,
  zero generation and empty references are preserved. Required members have
  no omission tag and still fail marshaling when unspecified.
  Both `UpdateResult.recovery_required` and `UpdateJobSummary.recovery_required`
  use `presence.Required[bool]`: `NewRequired(false)` preserves explicit false,
  while omission and null cannot become false. Validate original request bytes
  before decoding into a fresh model; these types do not replace schema checks.
  Plain Go pointers cannot distinguish absence from null. PATCH bodies never
  use null. The codegen config enables nullable types and supplies an import
  template for the local implementation. [`TestAPI01_OptionalNullableFields`,
  `TestReviewC04_PlanRateLimitPresence`, `TestReviewC06_RecoveryRequiredPresence`]
- **Request bodies are closed** (`additionalProperties: false`); responses are
  open for forward compatibility. [`TestAPI01_RequestBodiesAreClosed`]
- **Errors.** Every 4xx/5xx uses `ErrorEnvelope`; `ErrorCode` lists exactly the
  codes of `pkg/apierr` with the statuses of §14.6 and §13.11.
  [`TestAPI01_ErrorCodesMatchApierr`, `TestAPI01_ResponsesUseEnvelopeAndHeaders`]
- **Headers.** Every response has `X-Request-ID`. 429 and 503 have
  `Retry-After`. 202 responses with an `Operation` have `Location`. Admin and
  member side-effecting commands require `Idempotency-Key` (UUID). Modifying an
  existing resource requires `If-Match: "<resource_version>"` (412 mismatch,
  428 missing). New batches use `expected_generation` in the body (§14.5).
  Desired state supports `If-None-Match`/`304`.
  [`TestAPI01_IdempotencyAndPreconditions`]
- **Pagination.** `cursor` (opaque) and `limit` (default 50, maximum 100);
  responses carry `next_cursor`. [`TestAPI01_CursorPagination`]
- **Security.** Admin and member session cookies (`__Host-fvpn-admin`,
  `__Host-fvpn-member`), `X-CSRF-Token` on browser state changes, the
  enrollment token as `Authorization: Enrollment <token>`, Agent mTLS
  (`security: []` plus `x-fvpn-auth: agent-mtls`, because OpenAPI 3.0 has no
  mutualTLS scheme; see `x-fvpn-mutual-tls`), and the provider webhook
  signature. [`TestSEC01_SecurityPerRole`]
- **Desired versus observed** state are always separate fields; 202 is never a
  completion signal.
- **Hashes.** `payload_sha256` (usage event, §10.5) and `payload_hash` (update
  result, §13.10.3) are `canonjson.HashHex(doc, "<field>")`: SHA-256 hex of the
  RFC 8785 canonical JSON without that top-level member. `manifest_sha256` is
  the SHA-256 of the canonical JSON of the whole manifest envelope.
- **Signatures.** `{"signed": {...}, "signatures": [{"key_id", "algorithm":
  "ed25519", "signature_b64"}]}` over the canonical JSON of `signed`
  (`pkg/envelope`). Trust entries must have exactly one purpose; key IDs and
  public-key bytes must both be unique. Trust JSON rejects duplicate members
  and trailing data; envelope signatures reject repeated key IDs, including
  unknown keys. Purposes and keys: `release`, `desired-state`, `lease`,
  `recovery`, and central-only `ledger-epoch`. Never include a ledger-epoch
  key in node trust bundles; node checkpoints still use `recovery`. Node bundle
  loaders must use `NewNodeTrustStore` / `ParseNodeTrustStoreJSON`, which reject
  central-only keys. General trust-store constructors remain for central use. The §14.7 and §17.3 examples show a single `signature` object;
  this contract uses the uniform envelope instead (AGENTS.md §3).

Canonical JSON input is capped at `canonjson.MaxBytes = 1 << 20` (1 MiB),
matching the control HTTP body limit; oversized input fails before parsing,
sorting or hashing. Maximum container nesting is 256. HTTP handlers must also
bound reads before allocating an entire body (§14.6, §16.2).

Payment handlers must verify **`r.Body` before any parse** (§9.3, §14.4, §16.2).
`ProviderWebhookPayload` is `json.RawMessage` in Go and `unknown` in TypeScript;
it is not a parsed provider model. Preserve the original bytes for verification
and the durable inbox. Even remarshal of RawMessage can compact whitespace or
escape text; JSON.parse also loses large-integer precision. Do not verify a
reconstructed body or authorize membership from a return page.

Install `apierr.TrackResponse(w)` at the outer HTTP handler boundary and pass
that writer through middleware and handlers. `apierr.Write` refuses to append
an error once its `Written()` state is true, including an implicit 200 or flush.
An arbitrary unwrapped `net/http.ResponseWriter` does not expose prior writes;
wrapping it after the response starts cannot recover that information. Use
`http.ResponseController` for optional writer operations. Invalid pre-set
response/context request IDs are replaced with central UUIDs (§14.1).

## Browser role selector (D-032)

`GET /auth/session` and `POST /auth/logout` are existing browser routes outside
`/api/v1` and outside the 44-endpoint API. Their query parameter is recorded in
`openapi.yaml` under `x-fvpn-browser-auth`:

| Parameter | Type | Presence | Cookies |
|---|---|---|---|
| `role` | `admin` or `member` | Required only when both role cookies are present; ignored otherwise | `__Host-fvpn-admin`, `__Host-fvpn-member` |

With both cookies, absent or invalid `role` produces MALFORMED_REQUEST. Session
identity and logout CSRF context come from the selected cookie. The selector
does not grant a role. The task's proposed `/api/v1/auth/*` aliases do not exist
on main; adding them would violate the fixed endpoint count. No aliases are
introduced by this revision.

### Resolver delivery and evidence (D-056)

1. Verify the desired-state envelope and its node/incarnation, expiry and
   generation before using `dns.resolver_document` (§14.7).
2. A non-null reference binds `document_id`, `profile_revision_id`, **policy**
   `generation`, `content_sha256`, and `size_bytes`. Generation is the one that
   compiled the resolver document, not the desired-state config generation.
   Absent/null means no profile: apply only the designated resolvers.
3. Fetch `/api/v1/agent/resolver-documents/{document_id}` using node mTLS. The
   server authorizes only documents referenced by desired state **issued to
   this node**, in its current or immediately previous config generation.
   Missing/unissued documents both return 404 **NOT_FOUND**, retryable false.
   This additive code preserves the existing `RESOURCE_NOT_FOUND` used elsewhere.
4. The 200 body is the stored RFC 8785 document bytes, without an envelope,
   re-encoding, HTML escaping or trailing newline. Headers are
   `ETag: "sha256:<hex>"` and `Cache-Control: private, max-age=0`.
   Bound the read to 1 MiB, verify exact byte length and SHA-256 against the
   signed reference, then validate and call `node/dns.Apply`. A mismatch fails
   `dns_policy` and must never partially apply. The pinned strict-server template
   preserves these bytes; `json.RawMessage` alone would not preserve an Encoder's
   HTML escaping or appended newline.
5. Report optional/nullable `dns_policy_evidence` against the document actually
   applied. `generation` and `content_sha256` must come from that document,
   never a newer desired state. `applied_at` is nullable; unknown is not zero.
   Only `outcome=applied` with successful read-back is success; `partial`,
   `failed`, and `not_run` do not pass the check. Feeds contain only code, hash
   and rule count, at most 32 with unique codes. They never contain entries or
   queries. Absent/null evidence means no report, not successful enforcement.

The compiler's concrete document type lives in `internal/dnspublish` (generation
is stored beside the canonical bytes). The applier currently calls its evidence
members `policy_generation` and `document_hash`; the adapter maps these to
`generation` and `content_sha256`, adds the issued document ID, and translates
verified/apply results into the outcome and nullable time/error. This mapping is
an owner follow-up; existing producer fields are not renamed.

### Groups, diagnostics and feed status

Groups are immutable member groups (§15.2–§15.3). Discover them with the cursor
page and exact `code` filter, or create with `Idempotency-Key` and administrator
CSRF protection. Code and name are unique (409); `exit_count` counts attached
exits regardless of availability. Renaming means creating another group.
`PublicationRequest.group_ids` absent preserves membership, `[]` clears it, and
a supplied list atomically replaces membership together with intent under the
exit's same `If-Match`. Unknown IDs return 422 with a field detail. The admin
node detail exposes membership; `MemberExit` is unchanged.

A non-null signed `egress_probe` overrides the local `egress_probe_target`.
Absent/null retains existing local-or-skip behavior. Targets are 1–4 unique
TCP endpoints with IP literals; omitted `timeout_ms` means 2000 ms. This does
not authorize forwarding or relax isolation. Probe identity, team-controlled
destinations and exact temporary exceptions remain mandatory (§13.9).

`NodeCheck.detail` and feed status messages are limited to 500 characters and
must be sanitized before reporting: no secrets, subjects, tokens, raw member
addresses, feed entries, query names, credential-bearing URLs or raw bodies.
Threat-feed status is available only for `type=threat_feed` and describes its
active revision. Bootstrap-empty uses null last-good fields/age. Failed refresh
retains last-good content and increments failures; age remains a decimal string.
The approved hash is the approved snapshot, not proof of applied feed content.
Compare it and last-good hash with the actual per-node feed evidence, never
present desired as applied. Internal lowercase refresh reasons must be mapped
to public `ErrorCode`; no internal reason is copied directly into that enum.

The per-source feed interval is optional, default **21600 seconds**, within
300–604800; effective cadence is `max(product cadence, source interval)` (D-054).
OpenAPI defaults are annotations, not runtime initialization. The generated Go
field retains `int` with `omitempty` for source compatibility; owners must
materialize 21600 before validating/persisting/scheduling an omitted interval.
Explicit zero is rejected at the HTTP boundary. `attribution: null` remains
valid in the generated type and both payload schemas. The current lower-level
`dnspolicy.ValidateSource` still rejects blank attribution notes after policy
conversion; resolving that behavior is a policy/DNS owner follow-up.

## Signed documents designed here

- **Desired state (§14.7).** The signed object contains the §14.7 fields plus
  `schema_version`, `serving_release_ids`, `accounting_period`,
  `device_bindings` (§10.2), `member_rate_policies` (§11.2, §11.3),
  `node_capacity`, `dns` resolvers (ISO04) and the current `update` intent
  (§13.10.2), so the node gets the policy content it enforces, not only
  replaceable references (§14.7).
  Optional, nullable `dns.resolver_document` binds separately fetched canonical
  bytes; optional, nullable `egress_probe` binds the TCP probe destinations
  (D-056, D-058). Both are covered by the desired-state signature and the
  new resolver/probe vector; older vectors remain unchanged.
  Optional `revoked_release_ids` is a unique UUID array signed with the rest of
  the object (D-034). Absent and empty mean no additional revocations. A node
  must refuse installation and stop serving any listed release. This never
  widens the existing serving/allowed release intersections. Central services
  must keep revoked releases disjoint from approved and serving releases.
- **Update result (§13.10.3).** `policy_generation` identifies the desired-state
  `config_generation` actually applied when the result was produced. It must
  not be filled from the job's `generation` or merely the newest received
  desired state. This resolves the updater's previous config-generation alias
  ambiguity. The field remains required (D-049); persist exactly the reported
  value. `policy_refs` exists on desired state, not on UpdateResult.
- **Update target evidence (§13.10.3, §15.4, D-048).** Optional, nullable
  `UpdateTarget.policy_generation` and `policy_refs` expose the applied
  desired-state `config_generation` and policy revision references from the
  accepted result that produced the target's current evidence. Absent or null
  means no accepted result or unknown history. Readers must never infer zero;
  servers must never borrow the newest desired state. Explicit `"0"` and `[]`
  are known values, distinct from unknown evidence. References are unique UUIDs
  with at most 64 entries; generation is an exact uint64 decimal string.
  Examples retain the [original omitted shape](../../contracts/examples/valid/UpdateBatch.json),
  add [reported evidence](../../contracts/examples/valid/UpdateBatch.applied-policy.json)
  and [unknown evidence](../../contracts/examples/valid/UpdateBatch.unknown-policy.json).
- **Serving lease (§16.3).** `lease_id`, node and incarnation,
  `authorization_generation`, `config_generation`, `issued_at` (signed server
  time), `expires_at` (node lease end), `max_offline_seconds` (recommended
  default 86400) and per-member `lease_end` with `effective_service_end`.
  `ServingLease` describes the server and node rules: bounds, replay, monotonic
  deadlines and fail-closed behavior. The canonical concrete §16.3 example is
  [`serving-lease-signing.json`](../../contracts/vectors/serving-lease-signing.json).
- **Usage checkpoint (§17.3).** The §17.3 fields, signed with a `recovery`
  key; `recovery_record_id` is null when no restore happened in the epoch.

## Examples

`contracts/examples/valid/<Component>[.<variant>].json` and
`contracts/examples/invalid/<Component>[.<variant>].json`. The component is the
file name before the first dot. Every invalid example has an expected reason in
`invalid/reasons.json` (hand-written) or `invalid/reasons.generated.json`:

- `{"kind": "schema", "pointer": "/records/0/upload_bytes", "keyword": "type"}`:
  must fail OpenAPI validation (and JSON Schema validation where a schema
  exists) at that pointer with that keyword;
- `{"kind": "payload_hash", "field": "payload_sha256"}`: schema-valid, hash wrong;
- `{"kind": "signature", "code": "KEY_UNTRUSTED"}`: schema-valid, envelope
  verification fails with that code.

Envelope, usage-event and update-result examples are generated (signatures and
hashes must be exact); edit `contracts/internal/gen/docs.go` and run
`make -f mk/contracts.mk contracts-generate`. Every request body has at least
one valid and one invalid example, and every success response body has a valid
one [`TestAPI01_ExampleCoverage`]. `pkg/api` decodes every valid example into
the generated Go types with unknown fields rejected and checks that encoding
round-trips.

## How to add or change an endpoint

1. Find the requirement in the spec. New endpoints change the current count of 44 (including D-015);
   coordinate with the orchestrator and update `specEndpoints` and
   `specStatuses` in `contracts/openapi_test.go`.
2. Edit `contracts/openapi.yaml`: path, `operationId` (lowerCamelCase, stable),
   one tag (`admin`, `member`, `agent`, `webhook`), `summary`, `description`,
   `x-fvpn-spec` (starting with `§14.`) and `x-fvpn-requirements`. Reuse
   `components/parameters` (`Cursor`, `Limit`, `IdempotencyKey`, `IfMatch`) and
   `components/responses` for every error status.
3. Add schemas under `components/schemas` following the conventions above.
   Request bodies get `additionalProperties: false`; nullable members must be
   required unless explicitly approved (D-048). New error codes go into `pkg/apierr` (status, retryable, section)
   and the `ErrorCode` enum together.
4. Add at least one valid and one invalid example for each new request body,
   and a valid example for each new response body; add the reason of each
   invalid example to `contracts/examples/invalid/reasons.json`. Add new
   components to the round-trip registry in `pkg/api/api_test.go`.
5. Add a row to the table below.
6. Run `make -f mk/contracts.mk contracts-generate` and then
   `make -f mk/contracts.mk contracts-verify`. Commit the regenerated files.

A signed or hashed document that is also used outside HTTP bodies also gets an
entry in `SchemaTargets` (`contracts/internal/gen/schemas.go`).

## Spec decisions recorded in the contract

- **D-056:** deliver resolver content separately using a signed reference and
  node-scoped mTLS fetch; preserve exact bytes and report document-bound evidence.
- **D-057:** add immutable member-group list/create; no PATCH/DELETE. Rename by
  creating another group. Publication atomically replaces optional membership.
- **D-058:** sign probe configuration, expose bounded diagnostic/feed metadata,
  and default optional source refresh cadence to 21600 seconds. Version 1.1.0
  has 44 operations. Spec prose amendments remain pending authorization.

- The update batch targets page is part of `GET /admin/update-batches/{batch_id}`
  (`targets`, `next_cursor`) under D-007; D-015 adds bootstrap and D-056/D-057 add resolver delivery and groups, making 44 endpoints. §13.10.4's
  `targets_url` points to that resource.
- `POST /agent/usage-batches` returns 200 with per-event results: §10.6's 409
  (same key, different hash) and 422 (invalid event) outcomes are reported per
  event as `conflict` with `USAGE_EVENT_CONFLICT` and `rejected` with
  `VALIDATION_FAILED`/`METER_PATH_INVALID`, and `blocked_seq` names the event
  that stops ACK progress. Whole-request 403, 409 `LEDGER_EPOCH_MISMATCH`, 422
  and 503 remain.
- Field names follow each spec example: the update intent and update result use
  `incarnation_id` (§13.10), other documents use `node_incarnation_id`.
- Minimum serving version is an allowlist of release IDs
  (`release_support.minimum_serving_version.serving_release_ids`), never a
  lexical version comparison (§13.2).
- Release manifests add `rollback.required_free_bytes`, which the §13.3 table
  requires but the example omits.

- D-007 keeps the additional required members absent from the spec figures:
  `UpdateResult.stage` and `recovery_required` (§13.10.3); `Operation.resource`,
  `error`, `request_id`, `updated_at`, `completed_at`, and each `OperationStep`'s
  `required`, `observed_at`, `error_code`, `message` (§14.8); and
  `UpdateBatch.operation_id`, `requires_service_restart`, `reason`, `created_by`,
  `created_at` (§13.10.4). Nullability does not make a member optional.
  Schema-valid figures are [UpdateResult](../../contracts/examples/valid/UpdateResult.json),
  [Operation](../../contracts/examples/valid/Operation.json), and
  [UpdateBatch](../../contracts/examples/valid/UpdateBatch.json); their extra
  variants demonstrate explicit null, an explicitly non-required step, and an
  empty target page. Do not copy the shorter prose figures as request bodies.
- D-016: `device_limit` has no schema default. Tests explicitly send 3;
  the production limit remains a business decision. Prices, fair-use rates
  and thresholds in examples are TEST ONLY, not production settings.

- D-015 adds `POST /agent/bootstrap` (agent mTLS, no body, no-store): 200 once
  with `external_key_id`, `setup_key`, `expires_at`; subsequent calls get
  410 `BOOTSTRAP_CONSUMED` even with the original idempotency key. Before worker
  preparation: 409 `BOOTSTRAP_NOT_READY`, retryable true. After the delivery
  deadline while still unconsumed: 410 `BOOTSTRAP_EXPIRED`, retryable false.
  Enrollment responses remain secret-free. The enrollment service owns atomic
  delivery consumption, deadlines, and secret redaction; provider key expiry
  remains distinct from both delivery and enrollment-token deadlines (§6.4).
- AT07 reinstallation: optional `EnrollmentCreateRequest.node_id` binds to an
  existing Node. The enrollment service checks that its previous incarnation
  is revoked (otherwise 409 `NODE_INCARNATION_ACTIVE`) and it is not retired
  (409 `NODE_RETIRED`). Successful enrollment creates a new incarnation while
  retaining Node history, never by clearing revoked lifecycle. Both conflicts
  are retryable false; ordinary fresh enrollment omits `node_id`.
- `UpdateTarget.needs_attention` and `unconfirmed` are required booleans:
  central operator attention and lack of confirmation of the last issued job,
  respectively. The update service owns these observations.

- D-031: `POST /member/checkout-sessions` succeeds only with 201 and a
  `CheckoutSession` containing `checkout_url`. Provider failure is 503
  `DEPENDENCY_UNAVAILABLE` (retryable true; use the same Idempotency-Key).
  The former 202 alternative is removed: there is no API to retrieve a checkout
  URL from an asynchronous operation. This is revision 3's deliberate HTTP
  breaking change. Regenerate clients; the strict server's
  `CreateCheckoutSession202JSONResponse` no longer exists. Legacy outbox/session
  writers require owner reconciliation, outside mechanical consumer adaptation.
